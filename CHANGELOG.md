# Changelog

All notable changes to Agentic Hardware-in-the-Loop (Agentic HIL) will be documented in this file.

The format is based on Keep a Changelog, and this project follows Semantic Versioning while pre-1.0 changes may still move quickly.

## [Unreleased]

### Added

- **Every tool now declares what it does, in the field a host reads.** All 37 entries in `tools/list` carry MCP `annotations` (`title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, schema revision 2025-06-18), set from what each tool demonstrably does rather than from what its name suggests. Without them a host had the name and nothing else, and it blocked `project_config_reload_description` — which re-reads the authoritative file, writes nothing and touches no hardware — because it sits beside `project_config_set` and `project_config_create`, which do write; the operator reconnected the server twice instead. The reload, `com_read`, `can_read`, `bench_run_status` and `project_config_describe` are declared read-only; `flash_firmware` and `debug_start_session`, whose `load` mode programs flash, are declared destructive; `probe_target` is deliberately *not* read-only, because an SWD attach halts the core, which is the line the quarantine inventory (hardci-hq#97) already drew. Implements hardci-hq#101.
- The hints enforce nothing and nothing in the package reads them: what a call may do is still decided by the configuration's permissions and the machine-wide device locks. A tool added without annotations, one claiming `destructiveHint` beside `readOnlyHint`, or one whose class in `docs/mcp-hosts.md` disagrees with the table, fails a test by name; the install eval additionally asserts that the annotations arrive over stdio on a real installation.

### Fixed

- **`agentic-hil init` looked for attached hardware only when the project shipped an `agentic-hil.config.example.yaml`**, so a fresh installation — which has none — wrote `probe_id: null` and a placeholder target on a machine with the board plugged in, while the MCP server, which reads unconditionally, found that same board; it was reported as broken CLI discovery, and discovery had simply never run. A profile decides how a found bench is named and narrowed, never whether looking is permitted, so `init` now reads the bench either way and fills the template from the same fixed default `project_config_create` uses when the workspace has no profile of its own. A run that finds nothing says so — the result carries the discovery outcome instead of `null` and names `agentic-hil adopt-hardware` — and a test pins the two paths to one answer about one machine. Implements hardci-hq#104.
- **A serial port was identified by its kernel name, so it moved when a second adapter was attached.** `/dev/ttyACM0` and `COM7` are an enumeration order rather than an identity: plugging in a second ST-Link renumbered them, and an unchanged configuration could come to name a different board — flashing, resetting and writing to hardware nobody meant, with nothing in the result saying so. `com_ports.<name>` now takes a `serial_number`, the adapter's own USB serial, which on a Nucleo is the serial `probe_id` already carries. Set, it is the machine-wide lock identity, so the mutex follows the board instead of the name, and it is compared against the attached hardware before the port is opened: a port that has become a different board is refused with the new `com_port_identity_mismatch`, naming where the configured board actually is, rather than connected to. An entry that carries no `serial_number` but shares a `resource_id` with a configured probe is checked against that probe's serial, so a bench already on disk is protected without being edited. Discovery and `adopt-hardware` record the durable name on Linux (`/dev/serial/by-id/usb-..._<serial>-ifNN`, which udev builds from the device's own serial) and re-spell an existing kernel name to it; Windows publishes no openable stable name, so `device` stays `COMn` there and `serial_number` carries the identity alone. Existing configurations keep working unchanged and are named rather than refused — `doctor` warns, and every `com_ports` entry reports its `identity_source`. Implements hardci-hq#100.
- **An upgrade that moved nothing reported success.** `uv tool upgrade` exits 0 both when it upgraded and when there was nothing it could do, and `agentic-hil upgrade` read that code instead of the two version numbers it already held — so an installation created with an exact pin (which the Claude Code plugin's skill documents, and which `uv tool upgrade` can never move) came back `ok: true` with `previous_version` and `version` identical, `restart_required: true`, and uv's plain-text reason passed through unread. The operator restarted onto the same release and went on believing they had upgraded. The three outcomes are now three answers: a real change is `ok: true` naming both numbers, an already-current installation is `ok: true` with `already_current: true`, and one held at a pin is `ok: false` `upgrade_blocked_by_pin`. Only the pin is a refusal — a machine that is already newest has nothing wrong with it, and refusing there would make the command exit non-zero on every up-to-date host and break the provisioning scripts that run it unconditionally. Both unchanged outcomes set `restart_required: false`, because there is nothing new to load. The pinned refusal carries `pinned_version`, `installed_extras` read off the installed distribution, and `reinstall_command`, which keeps those extras where uv's own `agentic-hil@latest` hint drops `[can]` and silently takes CAN support off a bench that has it. Agentic HIL names that command and never runs it: which version a machine runs is the operator's decision, and a pin can be deliberate. Implements hardci-hq#99.
- The plugin skill's exact pin stays — it ships guidance for one release, and a package ahead of it answers differently — but now states why it is wanted, that `agentic-hil upgrade` cannot reach past it, and which line does while keeping the extras. README, the quickstart and TROUBLESHOOTING carry the three outcomes and the rule that no install line outside the plugin adds `==`.

## [0.8.0] - 2026-08-06

The entries below add surface — configuration keys, MCP tools, a resource, a changed generated default — so this is a minor under decision 0019, not a patch.

Three of them change what the tool refuses, and all three came from one working day of using it: the path trust check refused the standard Windows user folders and is gone, a generated configuration granted nothing and now grants everything, and quarantine fired where the failure could prove it never reached the board. What replaced the first is detection rather than prevention; what replaced the other two is a narrower rule that holds. A fourth came from the same day and adds rather than removes: a board written into the configuration is picked up without restarting the server.

All four then went through an adversarial review of the whole range, which found eight defects — three of them in the refusal changes themselves, including two failures wrongly classified as proving they never reached the hardware. Those are fixed here too. A reader deciding whether to upgrade should know that the refusal boundaries moved twice: once by design, once because the first attempt claimed more than it could prove.

### Added

- **A running server says when the configuration it enforces is no longer the one on disk.** It parses the authoritative file at startup and answers out of that version, which is correct and was silent: an operator who switched a debugger from `stlink` to `pyocd` got `pyocd` from `doctor` and `stlink` from `debugger_info` in the same minute, with nothing in either to say which read the file that exists now. Every result now carries `config_status` and `config_stale: true` once the two diverge, `debugger_info`, `project_config_describe` and `doctor` carry the block either way, and the comparison is a SHA-256 of the loaded bytes rather than a modification time — so an identical rewrite is not a change and a change under an unchanged timestamp still is. `changed`, `missing`, `unreadable` and `unknown` are four answers with four remedies — the description reload below, or a restart; restore *then* restart; repair readability *then* restart; nothing, because no file was read to compare against — and `reload_required` from a configuration write now comes off the same check. A file whose bytes are no longer UTF-8 is `unreadable` rather than a restartable change, because no restart can load it. `missing` is reserved for the error that actually says the file is not there, so a path that has become unreachable — an ancestor that is no longer a directory, a permission on the way down — is `unreadable` and gets repair remediation rather than restore-the-file. While the file is `missing`, `project_config_describe` answers out of the loaded policy instead of refusing: `permissions_in_force` is what this server still enforces and `document_source` says whether the values came from disk or from memory. A file that is there and will not parse is refused instead, still carrying `config_status` and `permissions_in_force`, because a caller has to be able to act on it rather than receive an internal error from under the MCP layer; the same normalization covers `project_config_set` and `project_config_adopt_hardware`, which read the document before they change it. `project_config_describe` takes one securely opened byte snapshot and answers both halves out of it, so a response can never pair `state: unchanged` with values read from a newer file. Nothing reloads on its own: the bench's description is re-read only on the explicit request below, and permissions are never re-read at all. Implements hardci-hq#77.
- An agent can change an existing project configuration over MCP, gated by permissions in the configuration itself (hardci-hq#80). Until now only creation existed: `project_config_create` wrote the file once and the file it wrote refused every further write, so every later correction was hand work on YAML. In the session that produced this decision, that ended with an agent printing a 24-character probe serial for a person to retype.
- **Two permissions, not one**, by the owner's decision. `permissions.allow_config_description_write` opens what the bench *is* — `target.*`, `debuggers.<name>.probe_id` / `executable` / `interface_cfg` / `target_cfg`, `com_ports.<name>.device` / `baudrate`, and every `can_buses.<name>` field except its permissions. `permissions.allow_config_permissions_write` opens the `permissions:` blocks. A single permission for both would have been a master key: set so an agent could enter a probe serial, it would in the same motion have let that agent write `allow_flash: true` on itself, at a point where nobody says so. The invariant from #71 therefore survives for the common case — the agent reaches the description of the bench, never its own authority.
- `project_config_set` applies named keys with scalar values, each checked against the shipped JSON schema, all of them or none. No argument takes a document and `value` admits no object and no array, so no subtree — and no `permissions:` block hidden inside one — can arrive as a value. The changed document is validated on a temporary file before it replaces the working one, a write is refused while a run or a session holds hardware (`config_write_in_open_run`), and `provenance` records what moved, when, and through which call.
- The split is enforced twice: once by the key model, and once by comparing the permissions actually present in the document before against after. The second check reads the document rather than the request, so it holds where a path parser would not — a permission that moved without `allow_config_permissions_write` fails the write whatever the key was called.
- `project_config_describe` answers, for this configuration in this state, which keys the caller may change, which it may not, which permission would open a locked one, each key's current value and its shape from the schema. Not a general list: after the split the answer differs with what an operator has opened, and a general one would be wrong for most callers. Reading needs no permission.
- New MCP resource `agentic-hil://reference/config-shape`: which sections a configuration has and what each is for, which are required, a worked Nucleo-F446RE example, how to change one over MCP, which permission opens which key, and what deliberately cannot be done. `config-schema` says what is *valid*; this says what a configuration *looks like*, which is what a caller needs in order to write one. Every value shape in it is read out of the shipped schema when it is served, so the two cannot drift — the same principle that makes a refusal and the `errors` resource read one catalogue.
- A `debuggers` / `com_ports` / `can_buses` entry can be added by setting a key under a name that does not exist yet, which is hardci-hq#76's case. The server writes that entry's `permissions` block itself, every flag false, so a device an agent adds can never arrive already allowed to be flashed.
- **A board plugged in after `setup` ran reaches the configuration without hand transcription** (hardci-hq#76). `project_config_adopt_hardware` over MCP and `agentic-hil adopt-hardware` at the CLI read the attached probe and fill in the identity keys that are still unset — probe id, the backend's executable, the detected controller, the probe's own COM device — through `project_config_set`, so the grants, the schema check and the `provenance` record are the ones already there. Both supply no value of their own, cannot name a `permissions:` key, and report a key that already holds somebody's value instead of replacing it; several attached probes, none at all, or a toolchain belonging to another backend are each an answer naming what to do next. Reading the probe is a hardware call and is treated as one by both paths: it takes the same machine-wide locks every board read takes (so a probe another server, run or terminal holds answers `device_busy`), it proves its audit trail writable before touching the board and records the read there, it quarantines fail-closed if the read raises, and on a version 1 configuration it needs the same `allow_probe` that `probe_target` needs. An entry that already names a probe with a different one attached is `hardware_mismatch` and no plan at all, because the identity keys describe one board between them; and the plan is carried into the write as a per-key expectation *and* as the description of the document it was decided against, so a placeholder another writer filled during the seconds the probe took to read refuses the write instead of losing to it — including when what moved is not a key this tool can set, such as the entry's `type` or the `probe_id` that chose which board was read. A concurrent permissions change does not refuse it, because no plan here reads one. An entry carrying its own `target:` block has the detected controller reported rather than written: that block overrides the project target for the probe that was read, so writing the top-level `target.controller` would change the fallback a *different* board uses. And giving the board back is a checked claim — a lease whose release is not confirmed leaves the probe quarantined and refuses the configuration write, instead of reporting a clean read of hardware this process is still holding.
- **A board written into the configuration after the server started no longer needs it restarted** (hardci-hq#98). New MCP tool `project_config_reload_description` and CLI counterpart `agentic-hil config-reload` re-read the bench's *description* — `target`, `debuggers`, `com_ports`, `can_buses`, minus every `permissions:` block — on explicit request, never automatically and never as a side effect of noticing that the file moved. Permissions are not re-read at all, in either direction and under no flag: the grants in force stay the ones parsed at startup, and a device this server has never seen arrives holding nothing, so it can be probed and read and cannot be flashed, reset, mass-erased or written to until an operator restarts. Everything outside those four sections is refused by name in the result — `version`, `workspace_root`, `state_root`, `debug`, `artifacts`, `validation`, `recovery`, `reports`, `logs` and the project grants — because each is either a permission wearing a description key's clothes or a section that mixes the two. Refused while a run, a session or an unresolved incident holds the bench (`config_reload_in_open_run`, `resource_quarantined`) and on a file that is missing, unreadable or does not load. Afterwards `config_status` stops calling the adopted description stale, and carries `permissions_source` whenever the grants in force came from the startup document rather than from the file — so the divergence stays visible without being adopted.

### Changed

- **Quarantine is reserved for an unknown physical state; a failure that can prove it never reached the hardware refuses instead.** Every quarantine trigger was inventoried and classified by whether it can prove its abort point (hardci-hq#97), extending the 0.7.1 `debugger_command_rejected` precedent from one trigger to all of them: a missing toolchain executable (pyOCD, ST-Link CLI, the debug server, GDB), an OpenOCD `-f` script or adapter that failed before the init-stage marker printed — the flash command now carries that marker too, in front of a `program` that runs `init` itself — a pyOCD probe or `target_type` refused before any connect, an absent ST-Link, an unopenable COM port whose handle is verifiably closed, a SocketCAN adapter whose `CanInitializationError` says it never joined the bus, a failed direct CAN read, and a read (`probe_target` / `debugger_probes_list`) whose backend reports that no target answered now refuse with their named `error_type`, `retry_safe: true` and no quarantine record, because each of those left the board exactly as the last call that did reach it did. Everything that cannot prove its abort point — an unconfirmed flash or reset, an exception mid-call, unconfirmed cleanup, a dead owner, a broken audit trail — quarantines exactly as before, and the self-resolving class under `recovery.auto_recover` is unchanged. This supersedes the 0.7.1 entry below that has an adapter which would not open, a target that would not answer and a configuration script OpenOCD could not find still quarantining unchanged: each of those refuses here where its phase evidence is present, and quarantines where it is not. A justified quarantine is now resolvable by a person who was told what they are signing: every quarantined result and `hardware_lease_status` carry `quarantine_guidance` — per reason: what was attempted, what is confirmed, what remains unknown, and the `physical_check` to perform on the board before `recover --confirm-safe-state` — out of one catalogue in `agentic_hil.knowledge`, with an explicit fallback for a reason recorded by another version.
- **A generated configuration grants every permission, and the MCP write path can only take one away.** `agentic-hil init` and `project_config_create` wrote every permission `false`, so a bench was inert until a person found the keys in a YAML file outside the repository and set them by hand — which cost this project's owner a full working day and is why this changed. Both now write every permission `true`, including `allow_raw_debugger_commands`, `allow_mass_erase` and `allow_config_permissions_write`, and the direction replaces the closed start: `project_config_set` writes `false` into a permission and no other value, refused both on the value the request carried and on the permissions present in the document before against after, so an agent can only ever reduce its own authority through it. That claim is deliberately narrow — regeneration is creation and may write open permissions again, and CLI paths are the operator's. Two grants the schema puts on a section rather than in a `permissions` block, `debug.allow_all_symbols` and `artifacts.allow_upload`, are now narrowable too, and `project_config_create` is held to the same open-run refusal and probe lease as every other call that reads a board. Implements hardci-hq#96.
- **A regeneration reads the board under the whole lifecycle a board read has, and the contracts say what the ratchet actually covers.** `project_config_create` held the enumeration lock and the discovered probe but not the configured entry's own `resource_id` alias, wrote no audit record for the read, and discarded what `HardwareLease.release()` answered — so a board another owner held through that alias could be connected to, and a lease left quarantined still came back as `ok: true` with the configuration rewritten under it. It now runs the same function `project_config_adopt_hardware` runs and is in `audited_hardware_tools()`, so a raised exception comes back as the standard structured quarantine instead of escaping. The generated header, the shipped schema, the `config-shape` resource and `project_config_describe` said the file could only ever narrow; that is true of `project_config_set` and not of regeneration, which grants everything to an entry it meets for the first time, so each of them now names the call the direction belongs to and describes the other door as it behaves — including that the permissions a regeneration carries over are the ones the *writing server loaded at startup*, so a narrowing made over MCP binds that path only after a restart. A server that never bound a configuration but finds one on the in-lock reread — the second of two racing servers — reads the board through that lifecycle too, rather than directly and unleased. And a terminal audit record that cannot be written now raises the incident on the coordinator: the leases are already back by then, so nothing was left to quarantine and the refusal used to carry the pre-failure clean lease status while the next hardware call went through. The security story is the small honest one: the MCP permission-write path can only narrow.
- **An OpenOCD entry that can drive a board is validated like one.** The starter entry was exempt from absolute-script validation and from `doctor` because it still held `interface/stlink.cfg` and `target/stm32f4x.cfg` — and pinning would meanwhile resolve `openocd` off `PATH` for it, so on a host with OpenOCD installed `agentic-hil init` left an entry that granted everything and drove a real program with two unvalidated relative script names. Autodetection no longer runs for the untouched starter entry, which makes it inert rather than exempt, and any entry that names a toolchain is validated whole and checked by `doctor`. Both halves of that are now decided honestly: "untouched" means the skeleton entry with no `probe_id`, `resource_id`, target identity or flash address in it, so a bench somebody identified resolves its toolchain from `PATH` like any other instead of being classified as a starter and skipped; and "can drive" includes the read model, so under version 2 — where reading needs no grant at all — an entry with every mutation permission false is still validated and still checked, because `probe_target` on it starts a real debugger. `agentic-hil init` says so in its next steps instead of promising a bench that works as written.
- **Closing `allow_config_permissions_write` announces itself in the result of the call that does it.** It is terminal for `project_config_set`: after it that call cannot move a permission in the file again. The result carries `permissions_frozen` — what stands frozen and at what value, read out of the written document, that the caller cannot undo it, and `agentic-hil init --force` as the command a person reopens the file with — so an agent cannot nail the bench shut in passing and leave its operator in front of a file they have to edit by hand. Generation and `init` report what they actually wrote rather than a fixed "everything is granted", and `flash_firmware`'s refusal while raw debugger access is granted now names the narrowing that resolves it.
- **A generated configuration permits firmware anywhere in the workspace.** `artifacts.allowed_roots` defaulted to `["build"]`, which no CLion, PlatformIO, or Zephyr tree builds into — `cmake-build-debug`, `.pio/build/<env>`, `out`, `Debug`, `zephyr/build` all miss it, so the list had to be curated before a single flash worked. `agentic-hil init` and `project_config_create` now write `allowed_roots: ["."]`: the whole workspace, recursively. The list was never what stopped an attacker. Containment in `workspace_root` is, and it is untouched — the artifact path still fails on a traversal segment, and a build directory that is a symlink or junction pointing outside is still refused as `within_workspace: false`, which no configuration key relaxes. `allowed_extensions`, `inspect_known_formats` and the SHA-256 of the bytes that reach a backend are unchanged. What the root list added beyond those was a restriction inside the operator's own project, which is still available by naming directories. Implements hardci-hq#82.
- **Nothing that already exists widens.** The new value reaches an operator through generation only. A configuration that names `["build"]` still means `build`, and one that omits the key is still read as `["build"]` — what an absent key means is exactly what an update may not change (decision 0018). `project_config_create` now carries an existing `allowed_roots` into the file it regenerates, alongside the permissions it already carried; without that, a hardware refresh would have replaced a narrowed list with the skeleton's.
- **A regenerated configuration keeps the artifact extensions its owner set.** `project_config_create` carried `artifacts.allowed_roots` over and left `artifacts.allowed_extensions` to reset, so a bench narrowed to `[".bin"]` came back out of a hardware refresh accepting `.elf` and `.hex` again — three format parsers where a person had permitted one, silently, on a call made to pick up a new probe id. With the roots naming the whole workspace, the extension list is one of the checks that still refuse a foreign artifact, which is exactly why it may not be the one that resets. `artifacts.upload_directory` and `artifacts.max_upload_size_mb` are deliberately not carried: they place a directory and size a payload rather than say what may be flashed, and the same call re-derives `state_root` from the environment on purpose — `debug.allowed_symbols` is carried while `debug.max_dump_size_bytes` beside it is not, and this is that line.
- **`artifacts.allowed_roots: []` is refused at load, by name.** An empty list is one obvious spelling for "no restriction" and equally the obvious spelling for "nothing at all"; here it always meant the second, in line with `debug.allowed_symbols`. The refusal names `["."]` for the whole workspace, naming directories for a narrower set, and `artifacts.upload_directory` for uploads only, rather than let one key mean opposite things to two readers.

### Fixed

- **A description reload validates the configuration it composes, not only the file it read.** Pinning skips an OpenOCD entry's script check when nothing the loaded document permits can drive it, so a version 1 file whose grants are all `false` loads with unvalidated relative script paths — and a reload put this server's startup grants behind exactly those. The composed object is now re-checked and a reload that cannot pass is refused. `permission_summary` also names the version 1 read grants (`allow_probe`, `allow_read`), which it had dropped, so a file that moves only one of them is reported as the divergence it is instead of being called agreement.
- **The abort point of a read is the backend's claim, never the absence of one.** A read-only one-shot is released without quarantine only where the backend positively says it reached nothing (`target_contacted: false`); a markerless failure — killed at its deadline, or a toolchain that exited confirming nothing — quarantines as the new `debugger_readonly_target_state_unconfirmed`, which a read-only re-read may not settle because it attests reachability and the open question is run state. Each backend now names that abort point where it has the evidence: OpenOCD when a target-not-detected classification *read out of its own output* meets an absent init-stage marker, pyOCD and ST-Link on their own connect-failure words, for the two read tools whose command drives nothing. An OpenOCD exit of 0 with the success marker missing answers `probe_unconfirmed` instead, as ST-Link's equivalent exit already did: it is the absence of a report, not a report that nothing answered, and it had been reusing the very classification the evidence rule accepts. Both of those exits now publish `target_state_unconfirmed`, with a catalogue entry of their own, because `target_not_detected` says the adapter was reached and no target answered — the abort-point claim this rule withholds, in the one field a caller reads. A PCAN `CanInitializationError` no longer claims the adapter never joined the bus: python-can raises it from four `SetValue` calls that run after `PCANBasic.Initialize` succeeded, so only SocketCAN can make that claim from the exception class.
- **`target_state_unconfirmed` describes an incomplete confirmation, not an absent one.** Neither backend needs every confirming line missing to reach it — OpenOCD decides on the success marker alone, so the init-stage marker may be in the same output, and ST-Link requires all of its expected lines — yet both catalogue entries said the toolchain reported nothing at all. The result now carries `operation_result` naming which markers arrived and which did not, on both backends, and the entries point at those fields instead of describing a run they cannot see. The quarantine is unchanged: a partial confirmation still names no abort point.
- **`doctor` no longer says a restart is the only way a running server adopts a changed file.** `config_status.compare_with_running_server`, on every `doctor` result, is where a digest mismatch is read, and it still promised restart-only; it now names `project_config_reload_description` for `target`, `debuggers`, `com_ports` and `can_buses`, and the restart for everything else — permissions included, which that call never re-reads.
- **`init` and `setup` no longer chmod an operator's configured paths.** The POSIX smoothing that removed group/other write from every user-owned ancestor of `state_root`, the authoritative config and the agent policy file outlived the configured-path trust check it existed to satisfy; only the MCP launcher chain is still mode-checked, and only it is still smoothed. The shipped guidance also said an unqualified "a permission revoked since startup is already in force" — true of the three configuration-write grants and of no hardware or per-device one, which stay at their startup values until a restart.
- **A reload never renames the document its permissions came from.** `permissions_digest` was moved onto a file whose grants happened to match the ones in force, so a later reload that did find a difference reported that intermediate file as the permission source and paired it with the startup `loaded_at` — two snapshots read as one. It now stays on the startup document for the life of the process, and whether the description in force *states* those grants is its own re-answered field.
- **`state_root` is checked for writability, not only reachability.** An existing directory this process cannot create in loaded clean and failed at the first lease, report or log write; it is now refused at load, with the field named. `config_status` also says which document each half of a stale answer came from (`description_source`, `description_reloaded_at`) instead of claiming everything came from startup after a description reload, and `tools/ci_linux.py` forwards pytest arguments as positional parameters so a `-k` expression or a path with shell metacharacters survives the trip — dropping only its own leading `--`, so pytest's own separator reaches pytest.
- **A COM port is correlated to a probe by the one hardware identity everything else uses.** The correlation stripped punctuation as well as folding case, on the grounds that it keys nothing — but the port it picks is written into `com_ports.<name>.device` by adoption, so a probe serial `AB-CD` matching a sole host port whose serial is really `ABCD` put a different device into an entry whose `allow_write` may already be true. A tie guard cannot see a single false match. A serial the two inventories spell differently is now not correlated at all, and the COM port is reported unavailable with the host inventory attached, for the operator to name.
- **The write comparison sees entries whatever the operator named them.** `permissions`, `provenance` and `allow_anything` are legal debugger, COM and CAN entry ids, and the description projection dropped every mapping key with one of those names at any depth — so an entry called `permissions` was outside the compare-and-swap *and* outside the check for whether a change needs `allow_config_description_write`. A concurrent repoint of that entry from one board to another was invisible, and discovery from the first board could still be committed onto it. The projection now removes the schema's grant locations and only those; a grant found anywhere else survives into it, so it needs the description right as well as the permissions right rather than neither.
- **A failed lease release is now in the audit trail.** Adoption writes the read as an `ok: true`, `lease_state: active` report before releasing, which is right, and then stopped: a release that failed returned `resource_quarantined` while `get_last_report` still described a clean active discovery and `classify_last_error` had no failure at all. The terminal outcome is committed before it is returned, and if that write fails the result is `audit_failed_after_action` rather than silence. The clean path re-commits too, so a persisted record never says `active` about leases that have been released.
- **A partial release is not reported as a released lease.** The aggregate over the enumeration and probe leases took the first non-`active` state it found, so one lease back and one in `cleanup_required` produced `lease_state: released` beside `cleanup_required: true` — and callers are told to treat any state other than null/active/released as blocking. States now aggregate worst-first, the incident's `quarantine_id` travels with them, and each lease's own state is carried so a partial release reads as one.
- **A per-debugger `target:` block is compared before it is reported.** Every override sent the detected controller to `unavailable` with "set this value yourself", including one that already held exactly that controller and one that deliberately held something else — adoption recommending the overwrite it refuses to perform. A matching override is now `already_current`, a conflicting one is `kept` with both values and no recommendation, and only an override with no controller at all is `unavailable`.
- **The opencode write restriction is gone, and `setup` says so instead of implying one.** It never worked. `setup --agent opencode` wrote the two protected trees into `permission.edit` as absolute patterns, and opencode does not compare that key against an absolute path: `write.ts`, `edit.ts` and `apply_patch.ts` all ask with `patterns: [path.relative(instance.worktree, filepath)]`, `evaluate` in `permission/index.ts` matches the configured pattern against that subject, and `Wildcard.match` anchors it `^…$`. Both trees are required to live outside the workspace, so the subject always reads `../../.config/agentic-hil/…` and nothing absolute can equal it. The restriction matched nothing, and unlike the `Write(…)` rule fixed in 0.7.1 it produced no warning to say so. Read out of the opencode source, because its documentation does not say what the patterns are compared against. A correctly relative pattern was written and then dropped again, because it would not have been worth what it claimed: opencode settles this at the prompt, and one "always" answer adds a session rule allowing every later edit that outranks anything the configuration holds — a lock a single click removes should not be presented as one. So `setup` now writes nothing for opencode and reports that it wrote nothing, naming `~/.config/opencode/opencode.json` and `permission.edit` as where the operator sets this if they want it; SECURITY.md carries the reasoning. What a repeat `setup` does do is take back the absolute patterns earlier releases left, by exact text and only where the operator has left them at `deny` — a rule that reads as protection and is none is worse than no rule, which was the whole of this defect. Their own patterns, and any of ours they have since set to another action, stay untouched and in their own order. A test ports opencode's matcher and rule evaluation and shows the removed patterns resolving to `ask` against the subject that host really produces. `claude-code` is unchanged and still gets its `Edit(//…)` rules; Codex still needs none. Fixes hardci-hq#84.

## [0.7.0] - 2026-08-03

Reading needs no permission any more; per-device exclusivity took its place. A run names the devices it touches and holds them from its first step to its last, against every process on the machine from one lock directory per user, and a run that dies gives them back instead of leaving the bench blocked. The server now answers for itself over MCP, so a caller with no source tree can look up what a backend field means or what an error wants without reading the implementation, and a failing result carries the fix rather than only the cause. `setup` split into a user half and a project half, so a configuration location the host refuses no longer takes the skill and the MCP registration with it. Where no configuration exists, an agent can generate one over MCP, and the file it writes is what locks it out of writing again.

### Added

- **An agent can generate a project's configuration, and locks itself out doing it.** A project with no configuration answered every tool with `config_file_not_found`, and there was no route past it that did not involve a person at a terminal. `project_config_create` generates one over MCP, filled from `bootstrap` hardware discovery — probe id, controller, the probe's own COM device — and from nothing else: the tool takes no arguments, so it can neither name another workspace nor supply its own content, and a profile lying in the repository does not decide what the board may be told to do. Every write permission in the generated file is `false`, including the new project-scoped `permissions.allow_config_write`, so the reach of the whole path is exactly the reach of reading, which decision 0018 already grants. A person sets `allow_config_write: true` by hand to let the agent regenerate the file later; even then it refreshes hardware facts and carries every permission over unchanged. The file says an agent wrote it, in a header comment and in a `provenance:` block.
- **The ratchet lives in the configuration, and nowhere else.** Two states, both readable from the one file a human inspects: no configuration for the workspace and an agent may generate one; a configuration exists and its own `permissions.allow_config_write` decides whether an agent may write it. There is deliberately no second state store. Deleting a configuration out of band does let an agent generate a fresh one — that is a downgrade, not an escalation, because what it can generate is the fixed deny-by-default skeleton and nothing else, so the round trip costs a human their customised permissions and gains an agent no capability it did not already have. Nothing on the MCP surface deletes or moves a configuration. Implements hardci-hq#71.
- **`mcp-stdio` starts for a workspace that has no configuration.** It binds the workspace and refuses every hardware tool with `config_file_not_found`, naming the one tool that can do something about it. Only an absent file takes that route: a configuration that exists and does not load is still a hard stop, because reading "broken" as "absent" would let a damaged file be replaced by a generated one, silently discarding the policy an operator wrote. The generation path also picks a `state_root` this profile actually accepts, falling back to `~/.agentic-hil/state` where the documented default under `%LOCALAPPDATA%` is rejected (#64), and returns the same actionable refusal as the CLI where no location passes.
- **Reading needs no permission; exclusivity took its place.** The risk of generous read access in a HIL tool is not damage, it is a false green: a test that disturbs the object under test unnoticed produces a result nobody should trust. That happens when an observation from outside reaches into a running test, and a read permission never prevented it — it only raised the cost of starting, four flags set by hand before the first real Nucleo run did anything. So probing, COM reads and CAN reads need no grant, including the three reads that do perturb the target: attach with halt, CAN receive with ACK, port open with DTR. `allow_flash`, `allow_reset`, `allow_write`, `allow_mass_erase` and `allow_raw_debugger_commands` are untouched and stay deny-by-default. Implements decision 0018.
- **A run holds its devices, machine-wide, for as long as it runs.** The lease each call took was never exclusivity: it ended with the call, so between two steps of a test the board was free. `agentic-hil test-reactor` now locks every device its plan names before the first step and releases them after the last, and refuses a device the plan does not name — the plan is what the mutex can lock, so it has to be the honest record of what a test touches. Contention refuses with `device_busy` and names the holder (pid, host, frontend, run label, since when); waiting happens only when asked for, with `--wait-s`, and is bounded.
- **Devices are a base class, and the agent path got the same run boundary.** Debugger, UART and CAN each derived their own lock name and reached for the mutex in their own shape; the new `agentic_hil.devices` carries the identity, the mutex and one execution shape (`Device.execute(service, action, arguments)`) for all of them. Identity comes from the hardware — `resource_id`, probe serial, serial device, adapter and channel — never from the name of the config entry, so two entries describing one physical unit, such as an ST-Link and its virtual COM port under a shared `resource_id`, collapse to one lock. A declared set is taken in one all-or-nothing acquisition sorted by lock key, so two runs with overlapping devices cannot each hold what the other needs next, and a run whose third device is busy has already given back its first two before the refusal returns. The DUT is deliberately not a device: it is what the devices drive. A debugger entry with neither `resource_id` nor `probe_id` has no hardware to be named after — OpenOCD cannot enumerate probes — so its lock falls back to the toolchain and `bench_run_start` says so in `warnings` instead of presenting it as an identity.
- **`bench_run_start` / `bench_run_stop` / `bench_run_status` close the gap over MCP.** An MCP call took its device *per call*, so an agent driving flash → reset → read held nothing between the steps, and decision 0018's promise held for `agentic-hil test-reactor` only. A run is now declared once with `devices: [{"kind": "debugger"|"uart"|"can", "id": "<config entry>"}]` and holds them until it is closed; inside it only the declared devices may be touched, and a device already held fails the declaration immediately naming its holder. There is deliberately no idle timeout — dropping a device that may be mid-operation is the silent failure exclusivity exists to prevent. A run ends on `bench_run_stop`, on client disconnect (stdin reaches EOF and the server releases it while shutting down), or with the process, where the operating system drops the advisory lock.
- **The lock lives in one place per machine.** `~/.agentic-hil/device-locks`, keyed on the physical device, never under `state_root`: on 2026-08-02 two sessions held the same Nucleo and could not see each other because their `state_root` differed, and a lock kept per configuration is not a bench lock. The home directory is the only location whose ancestors pass this project's own trust check on a stock profile of either platform; the location is fixed and has no environment override, because an override is how two sessions diverge again. Reach is every process of one user on one machine: a directory shared across users is either writable by principals the trust check rejects or needs root to create.
- **A crashed run no longer blocks the bench.** Ownership is the operating system's advisory lock on the lock file, which the kernel drops when the holding process dies. No quarantine, no `recover --confirm-safe-state`, no waiting — the path that held up a run on 2026-08-02. The next owner reports what it reclaimed rather than silently reusing the board.
- **Passive modes are selectable and reported.** `comports.py` did not touch DTR or RTS and therefore took pyserial's defaults, which raise both on open; on a board that wires DTR to reset, listening to a target restarted it. `com_ports.<name>.assert_dtr` and `.assert_rts` now decide it, applied before the port is opened rather than after, both defaulting to the previous behaviour. They are reported in `com_ports_list` beside the device, so a reader can tell a passive observation from one that reset the board. With `can_buses.<name>.listen_only` they are no longer a precondition for access, but they remain the way to observe a target provably undisturbed.
- **The server publishes what it knows about itself over MCP.** `resources/list` and `resources/templates/list` answered with empty arrays and `resources/read` did not exist, so the only way to learn which fields a debugger backend needs, which `target_type` a board takes, or what an `error_type` means was to read the implementation. Measured over two bring-up sessions: 17 such reads, 10 of them inside the *installed* package under `site-packages`, which is what a caller who installed with `uv tool install` and has no source tree is left with. Six resources under `agentic-hil://reference/`: `debugger-backends` (which of `type`, `executable`, `probe_id`, `target_type`, `interface`, `interface_cfg`, `target_cfg` and `flash_address` each backend requires, discovers, or ignores; when `probe_id` becomes mandatory; when `flash_address` is needed), `errors` (every `error_type` with its meaning, ordered fix, and the wrong fix that looks right), `target-support` (which field names the target per backend, known-good Nucleo-F446RE values, and the fact that pyOCD target types come from installed CMSIS packs), `platform-paths`, `lease-lifecycle`, and `config-schema`. Two resource templates serve one entry each: `agentic-hil://reference/errors/{error_type}`, optionally scoped with `:<field-or-backend>`, and `agentic-hil://reference/debugger-backends/{backend}`. `initialize` names them, because it is the only thing said before the caller decides anything.
- **A failing result carries the fix, not only the cause.** New `remediation` (ordered steps) and `do_not` (the wrong fix that looks right) travel beside `likely_causes` wherever a fix is known: every `unsafe_configured_path` refusal, and per backend `target_not_detected`, `adapter_not_found`, and pyOCD's `target_type_invalid`. A rejected configuration path now names a location whose ancestors pass the trust check and rules out relaxing an ACL, which is the obvious response and the wrong one. An `error_type` with no written fix gains neither field. Results and the `errors` resource read one catalogue, so the reference cannot drift away from the refusal.
- **`agentic-hil upgrade`** upgrades the installation running the command, then verifies it. It selects the manager that owns this interpreter — `uv tool`, `pipx`, `uv pip`, or `pip` — rather than whichever `agentic-hil` resolves first on `PATH`, so a second copy is never upgraded by mistake. `--agent <agent>` (repeatable) reinstalls that agent's skill afterwards from the new code, in a temporary directory so no project config is read. The result reports `previous_version`, `version`, `manager`, and `restart_required`; agent hosts must be restarted to load the new MCP server.
- With `agentic-hil.config.example.yaml`, `setup` and `init` locate STM32CubeProgrammer, require one ST-Link, identify it via HOTPLUG, match its COM port by USB serial, and write host values externally. This pre-policy path cannot reset, halt, erase, flash, run raw commands, or access serial I/O.

### Changed

- **`setup` is split along its scope boundary and still works as one command.** One transaction, one rollback set and one smoothing pass spanned two scopes with different lifetimes: skill plus user-level MCP registration (user scope, once per user and agent), then authoritative config plus `doctor` (project scope, once per project). New `agentic-hil agent-install --agent <agent>` is the user half — skill, registration, persistent-trusted-executable check — needing no workspace and no readable configuration; it writes only under the invoking user's home, so per user and per machine, not shared with another OS user on the host. `agentic-hil init` is the project half: it now runs `doctor`, takes an optional `--agent` for the write restriction, and keeps a config it finds instead of refusing, so both halves are idempotent. `setup` runs the two in order, and rollback stays inside its own half in both directions. So on a stock Windows profile, where `%APPDATA%` fails the ancestor trust check, the configuration refusal no longer takes the skill and the MCP entry with it: `setup` reports `ok: false` with `scopes.user.ok` true, leaving a working agent and one location to fix. `--force` still reaches the user half only; rewriting an authoritative config remains `agentic-hil init --force`.
- Profiles may request flash, reset, artifact, and UART access; raw commands and mass erase stay denied. The config a profile produces is version 2, so a probe or read request in a profile written against version 1 is already satisfied and is dropped rather than written into a file that version would refuse. No profile means everything that writes or changes state stays denied; existing operator configs remain untouched.
- Windows discovery includes versioned `C:\ST` CubeCLT, PATH, standalone CubeProgrammer, and CubeIDE installs.
- **Configuration `version`, and an explicit migration.** A file with no `version:` key is read under version 1, where reading still needs `allow_probe` / `allow_read`, so an update never widens what an existing bench allows. `version: 2` selects the new model; a version 2 file that still carries a read permission is refused by name with the key to remove, because ignoring it would leave an operator believing a flag still gates something. `agentic-hil init` writes `version: 2`.
- `agentic-hil doctor` checks the probes whose toolchain the configuration pinned rather than the probes that may be read. "May be probed" is now universal and says nothing about what a bench is meant to drive; using it would have made a freshly written config demand a debugger toolchain before `setup` could finish.

### Fixed

- **A device lock key folded case on Windows and preserved it everywhere else.** Every key was built through `os.path.normcase`, which lowercases on Windows and does nothing at all on POSIX. That is the right rule for the two components that really are host paths — a debugger executable, and a serial device such as `COM7` or `/dev/ttyACM0` — and the wrong one for the components that name hardware: a `resource_id`, a probe serial, a CAN channel. `0669FF` and `0669ff` are one ST-Link on every operating system, so two config entries naming one physical unit in two spellings collapsed to one lock on Windows and stayed two locks on Linux and macOS, with no error on either — the same bench, two different exclusivity guarantees. Opaque hardware identifiers now fold identically everywhere, and path-like values still fold as their own filesystem does. Because folding can also merge, config load now refuses two entries whose `resource_id` values differ only in case: an identical id is still how an ST-Link and its virtual COM port are declared one unit, but two spellings of one id are a question for the operator rather than a merge behind their back. Device locks are ephemeral files under `~/.agentic-hil/device-locks/` that the operating system drops with the holding process, so changed keys need no migration.
- `agentic-hil setup` reported a rejected default state directory under `field: user_config`, labelling a `state_root` failure as one about the configuration file — and, with remediation attached, it would have proposed moving `config.yaml` to fix a state directory.

## [0.6.0] - 2026-08-02

An unattended loop no longer stops at every quarantine. The owning process clears the failure classes it can actually verify, and the audit records what verified them.

### Added

- **The owning process recovers its own quarantines.** A blocked hardware call attempts recovery before refusing: it reaps this owner's leftover debugger processes, verifies the safe state, writes a `recovery: machine_attested` report, and then runs. Previously a quarantine could only be cleared by a person running `agentic-hil recover` — for every class of fault, including ones no person can add information to, such as an OpenOCD process that died mid-cleanup.
- **`recovery.auto_recover` policy** (`off`, `readonly`, `reset_halt`; defaults to `reset_halt`) with `recovery.max_attempts` (default 3) bounding attempts per incident. `readonly` reaps processes and re-reads the probe, which connects without resetting on every backend and therefore cannot alter the state it attests to. `reset_halt` additionally drives a reset-into-halt, which is what settles an unconfirmed flash, reset, or debug-session start. Set `readonly` if anything on the bench reacts to a target reset.
- **`lease-status` reports why, not just that.** New `cleanup_reasons`, `auto_recoverable`, and `auto_recover_policy` fields answer whether to retry or fetch an operator. `cleanup_reasons` also travels on lease-carrying tool results and into the project record, so a second process sees it. The reason previously existed only inside the on-disk marker's `errors[]`, so classifying an incident meant opening state files under the state root.
- **Machine-recovery provenance in reports:** `safe_state_predicate` (`readonly_probe` or `reset_halt`), `auto_recover_policy`, and `auto_recover_policy_source` (`config` or `default`). A config that never names the policy gets the default plus a one-time `warnings` entry the first time recovery resets its target.

### Changed

- One-shot debugger failures no longer share one undifferentiated quarantine reason. Read-only calls (`debugger_probes_list`, `probe_target`) raise `debugger_readonly_result_unconfirmed`, which a re-read settles; `flash_firmware` and `reset_target` keep `debugger_result_unconfirmed`, which needs the `reset_halt` predicate because either may have left the target running.
- A one-shot call that quarantined kept its lease registered but unreachable, so nothing in the process could ever resolve it. The lease is now retained for recovery and released once the safe state is verified.
- Under the default policy a failed `debug_start_session` load is settled by machine recovery instead of waiting for an operator. Recovery halts and never runs the target, so control is not handed back to a partially written image; flashing and running it again stays an explicit, permissioned act. Set `recovery.auto_recover: "readonly"` to keep the previous behaviour.

Excluded from machine recovery regardless of policy: a broken audit (`*_audit_broken`), an incident adopted from an owner that died, a mix of reasons, a still-active sibling lease, an incident whose resources this owner no longer fully holds, and any bench without `allow_probe`. `reset_halt` degrades to `readonly` when the bound probe lacks `allow_reset`. The `machine_attested` report is written before the state transition, so a failed audit write aborts the recovery instead of silently unblocking hardware.

### Fixed

- The CAN receive-queue drain budget bounds time spent talking to the adapter instead of also covering the `queue_clear_start` audit write that precedes it. The one-second deadline was armed before that write, so a slow first append — a cold runner creating the JSONL log while a scanner holds it — could consume the whole budget and break the loop before a single frame was read, failing `can_session_start` with `can_queue_clear_limit` and `frames_drained: 0` on a queue that was never touched.

## [0.5.0] - 2026-08-02

### Changed

- **BREAKING — permissions moved onto the device they authorize.** The top-level `permissions:` block is gone. A debug probe carries `allow_probe`, `allow_flash`, `allow_reset`, `allow_raw_debugger_commands`, and `allow_mass_erase` under `debuggers.<name>.permissions`; a serial port and a CAN bus each carry `allow_read`/`allow_write` under `com_ports.<name>.permissions` and `can_buses.<name>.permissions`. Every flag stays deny-by-default and now has exactly one owner, so enabling flash on a bring-up board cannot grant it on a second board sharing the project config. Loading a config that still declares the old block fails closed with a per-flag migration map instead of a bare unknown-field error.
- **BREAKING — every debug probe is a named `debuggers` entry.** The single top-level `debugger:` block is gone; the name is the routing key a test plan step uses. A project with exactly one probe binds it automatically and needs no name anywhere. The MCP tool surface drives that single bound probe: with several configured, debugger tools refuse with `not_supported` and point at `agentic-hil test-reactor`, which routes per step by name. Two entries that resolve to the same physical probe are rejected at load. A probe_id is required before a board is actually driven rather than at load, so the ids can still be discovered — it is the only field the backends turn into `adapter serial` / `sn=` / `--uid`, so without it two names would drive whichever probe is plugged in.
- **BREAKING — the `devices:` block is gone.** It only bound a debugger to a UART, and both are now addressed by their own names. Test-plan steps carry `debugger: <name>` for flash/debug actions and `port_id: <name>` for UART actions instead of `device: <name>`. A per-board target override moved from `devices.<name>.target` to `debuggers.<name>.target`.
- **BREAKING — the test plan format is version 2.** Version 1 steps addressed a `device:` that no longer exists. A version 1 plan is refused by name, with the key that replaced it for each action, rather than failing on a bare version mismatch.

### Fixed

- A pyOCD `probe_id` is resolved to the one full probe UID it selects before any board is driven. pyOCD matches `--uid` as a case-insensitive *substring* of a probe's unique ID and strips an optional `<type>:` prefix first, so a configured value could select a board the operator never named and two different values could select one board. Zero matches and ambiguous matches are refused before the command runs; config load itself stays hardware-free.
- Config load rejects one `probe_id` that contains another, and treats `stlink:ABC` and `ABC` as the same selector, since that is how pyOCD reads them.
- A project with several probes and no `probe_id` yet now loads, so `agentic-hil debugger-probes` can be used to discover the ids. Requiring the id at load made the documented bootstrap circular: the ids could only be learned from a config that would not load without them. The requirement moved to the point where a board is actually driven, and the refusal names the discovery command and OpenOCD's inability to enumerate.
- A firmware artifact reached through a symlink or junction that leaves the workspace is now refused by name. Containment was computed lexically, so such a path was reported as `within_workspace: true` and fell back to the misleading "must be a single-link regular file" wording — on exactly the case where naming the reason matters most.
- A debug dump into an allowed artifact root that is itself a link inside the workspace is no longer falsely refused. `validate_output_path` resolves symlinks while `artifacts.allowed_roots` are pinned lexically, so the two disagreed whenever a root was a link (pre-existing).
- A per-probe `debuggers.<name>.target` override is applied when that probe is bound, including the automatic binding of a single configured probe. It was parsed and then only honoured for probes other than the bound one, so on the supported single-probe path it was silently dropped.
- A firmware artifact outside `workspace_root` is now refused with that reason instead of "must be a single-link regular file" carrying a `backend_error` about an *output* file, and the `validation` block reports `within_workspace`. A debug dump whose `output_path` leaves the workspace is refused by the same check during reactor preflight rather than after the plan has already flashed and halted the board.
- `write_intel_hex_file` requires a `workspace=` argument and passes it to `atomic_write_text`, so the one write primitive an agent aims at a path of its own choosing carries containment at the write itself, not only in the caller's earlier directory check.
- `stage_for_backend` refuses an artifact whose content was never validated. With `validation.require_existing_file: false`, validation of a file that does not exist yet skips the size, format-plausibility and hash checks entirely; a file appearing before staging was then flashed unchecked.
- Refusals raised while staging an artifact no longer quarantine the probe lease. They happen before the backend is called, so they now carry `side_effect_committed: false` instead of being recorded as an unconfirmed hardware effect that puts a bench into recovery.
- `agentic-hil doctor` resolves and version-checks the debugger toolchain of every probe that grants `allow_probe`, reporting each result under `debuggers.<name>.check`. It previously checked only the bound probe, so a multi-probe project — where nothing is bound — reported `ok: true` with the check silently skipped and no named entry verified at all. The check proves each probe's toolchain resolves and runs; it does not open a probe or contact a target, so it cannot detect an unplugged board or a wrong `probe_id`.
- `agentic-hil debugger-probes` enumerates every probe-enabled debugger instead of refusing whenever no single probe is bound. Probe discovery is how an operator obtains the serial numbers a multi-probe config requires, so it has to work in exactly that config; each backend enumerates all attached probes anyway.
- Two debuggers naming the same `probe_id` are rejected even when their `resource_id` values differ. `resource_id` only renames the coordination lease, so it could previously mask two names pointing at one physical board.
- `classify_last_error` works without a bound probe. It reads the last recorded failure of any tool, so a UART-only or multi-probe project can ask what went wrong instead of being told the tool is unsupported.
- A COM port granted `allow_write` without `allow_read` can now actually be written to. Opening the session was gated on `allow_read` alone, and the session is the only route to the port, so the grant was unusable; the background reader and the buffer drain still require `allow_read`.
- A `run_until_breakpoint` step that omits `timeout_s` no longer fails its own contract. Execution sent an explicit `timeout_s: null` that the `debug_continue` schema rejects, while preflight had validated only the call the plan actually described.
- A flash step refused for `allow_mass_erase` says so, instead of naming the `allow_raw_debugger_commands` flag the operator can see is `false`.
- Backend `likely_causes` and error summaries name `debuggers.<name>.executable`, `.flash_address`, `.target_type` and `.probe_id` instead of the removed singleton `debugger.*` keys, so following the remediation advice no longer produces a config that cannot load.

### Removed

- **BREAKING — test adapters.** The `adapters:` config section, the seven `adapter_*` MCP tools, the adapter bridge service, and the simulated NTC example are removed until the first real adapter exists. CAN process bridges are unaffected.

## [0.4.0] - 2026-07-31

### Added

- `agentic-hil setup --agent <agent>`: one-shot project setup (authoritative config + skill install + MCP registration + doctor) in a single command. It prepares a safe external `state_root` and, before the fail-closed trust validators run, silently tightens the operator's own group/other-writable directories along the config, state, and MCP-launcher chains so setup succeeds on default umask-002 / private-group homes without hand-fixing permissions. Only user-owned components are changed — the walk stops at the first foreign-owned or symlinked ancestor, never touching shared or system directories — and every change is reported in the result's `permission_changes`.
- Per-agent USER-level MCP registration by `setup`: Codex `~/.codex/config.toml`, opencode `~/.config/opencode/opencode.json`, and Claude Code `~/.claude.json`. Each file is merged directly with secure atomic writes outside the repository to preserve the policy trust boundary; registration is idempotent and fails closed on unsafe files.
- Claude Code plugin (`plugins/agentic-hil/` plus `.claude-plugin/marketplace.json`): distributes the version-matched setup skill without persisting an unverifiable portable MCP command. The skill requires an exact persistent package install and delegates user-level MCP registration to `setup`, which records the verified absolute console-script path. The repo is also discoverable by the Vercel `skills` CLI (`npx skills add`) for cross-agent skill distribution.
- Containerized installation evaluation (`evals/install/`): a real agent CLI installs Agentic HIL from the documented guide, then a root-owned verifier judges the result with the home and workspace read-only, without network or credentials, from host-generated evidence rather than from what the agent reported. Every combination runs at least twice and disagreeing repetitions trigger further runs, because a run that passes because the agent did nothing is a real failure mode. Hardware commands are shadowed on `PATH`, so reaching for one is recorded and fails the run. `*-without-skill` cases uninstall the bundled skill between the installing session and the measured one, which is what separates its contribution from the tool descriptions and the registration.

### Changed

- The bundled skill is named `agentic-hil` and is written around routing: a request-to-tool table over the whole tool surface, the raw commands that are never a substitute, and what to do when a tool returns `permission_denied` — report the refusal, diagnose through the gate, and ask before changing a permission. `setup` removes the copy installed under the superseded name, but only a file carrying this project's own frontmatter, so a foreign skill that happens to use that name is left alone.
- MCP tool descriptions name the raw commands they replace, which is the one routing surface every session sees without a skill being discovered first, and the only one available to an agent with no skill mechanism.
- The VMware install-loop harness is retired in favour of the container evaluation. The hardware test plans, per-backend configuration templates, and MCP probe move to `evals/hil/`, together with what a containerized hardware executor needs: device passthrough and one run at a time.
- MCP registration stores only a verified absolute persistent console-script path and rejects bare PATH commands, transient runners, workspace virtual environments, unsafe symlink chains, and unsafe ownership or permissions. Stable user-owned pipx/uv-tool links remain supported after their link and resolved target chains pass validation.
- A refusal says that it is the answer. `initialize` returns server instructions, so a session knows before its first decision that hardware requests are answered by these tools; a permission refusal, an MCP entry conflict, and a skill conflict each carry a `next_step` naming whose the file is and that editing it, deleting the entry, or rerunning with `--force` is not a resolution. Measured: with wording that only named the obstacle, ten evaluation runs rewrote the operator's MCP entry by hand and reported success.
- `doctor` reports how the running package was installed. An editable installation copies nothing, so the code enforcing the hardware policy is whatever a source tree holds at the time.
- Setup restricts the agent CLI's own write tools on the policy files as its last step, rather than using a path rule that would also stop `mcp-stdio` from reading the file it must read.
- `AI_AGENT_QUICKSTART.md` leads with `agentic-hil setup`, documents the MCP registration as user-level per agent, and adds guidance for pip-less environments (Ubuntu 24.04+/PEP-668).

### Removed

- `llms.txt`. Nothing linked to it, nothing served it, and its own onward references were bare filenames an external fetcher could not resolve — so it was a third copy of the installation instructions with no reader to justify it, and its tool list had silently fallen to 15 of 36 tools.

### Fixed

- `doctor` reports the command a registration would accept — the verified persistent executable — instead of the bare name `agentic-hil`, which is the one form registration refuses because `PATH` decides it afresh every session. When no trusted executable exists yet it says so rather than printing something that would be rejected.
- A forbidden root is matched in both of its shapes. macOS reports its temporary directory as `/var/folders` while a path under it resolves to `/private/var/folders`, so a command placed there was compared against a root it could never match and passed a check meant to reject it.
- The refusal of an untrusted MCP command names the offending directory, its mode, and its owner. One bad ancestor of a shared prefix condemns every launcher below it, and a caller cannot fix a directory the message does not identify.
- The Windows environment setup no longer reports "no untrusted writers" when `Get-Acl` is unavailable; it reads the same access rules through the .NET accessor instead of turning the preflight into a silent no-op.
- The packaged skill is recognized on a Windows checkout. git converts it to CRLF there and the frontmatter is matched line by line, so the installer read its own skill as a foreign one and refused to update it.
- A world-writable coordination lock directory is refused when hardware is acquired, which is where coordination state is created since it became lazy, rather than at construction where nothing was built yet.
- Rewriting the skill registration block no longer fails on Windows. The block names the skill's absolute path and `re.sub` reads escapes in a replacement string, so a second write of a path under `C:\Users\...` died on a bad escape. Only `skill-install` followed by `setup` took that branch, which is why a plain `setup` never hit it.
- A rejected setup keeps what an earlier command installed. Rollback restores the state setup found, so a skill from a standalone `skill-install` or a config from a standalone `init` survives on purpose, and the refusal now names a skill left behind without a registration to go with it.

## [0.2.0] - 2026-07-06

### Added

- Debug sessions now classify abnormal target stops: unexpected breakpoints return `unexpected_breakpoint`, Cortex-M exception/fault contexts return `target_exception` with frame, signal, and suggested next actions, and session status picks up asynchronous stop records.
- Typed GDB/MI debug sessions for the OpenOCD backend: the eleven `debug_*` tools now run real sessions (start/stop/status, breakpoints by symbol or file:line, continue/halt with structured stop reasons, symbol resolution, Intel-HEX memory dumps) against OpenOCD's gdbserver, gated by `debug.allowed_symbols`, `debug.max_dump_size_bytes`, and the existing permission model (raw-command mode disables typed debugging; `load` mode requires flash permission). The session's gdbserver is pinned to `localhost` on an ephemeral port and torn down with the session.
- pyOCD debugger backend (`debugger.type: "pyocd"`) with probe/flash/reset support, `target_type` selection, and pyOCD-specific error classification.

### Changed

- Firmware flashing no longer resets the target by default. Pass `reset_after_flash: true` to `flash_firmware` to request the previous post-flash reset behavior.
- Removed the separate `permissions.allow_reset` policy field; reset remains a typed debugger action instead of a separately gated permission class.

### Fixed

- Hardened the MCP transport and sessions: bounded JSON-RPC message size, COM sessions recover after device disconnects, `com-stdio` relays board output while stdin is idle, artifact validation streams instead of loading whole files, and host serial-port discovery is gated by `allow_com_read`.
