# Changelog

All notable changes to Agentic Hardware-in-the-Loop (Agentic HIL) will be documented in this file.

The format is based on Keep a Changelog, and this project follows Semantic Versioning while pre-1.0 changes may still move quickly.

## [0.20.0] - 2026-08-30

### Added

- **Both non-intrusive read claims are measured now, not only documented.** The ST-Link hot-plug read (#348) and the pyOCD attach read (#349) each ran the five-pair SysTick measurement on a real NUCLEO-F446RE, through the MCP tools inside one bench run: five read pairs whose counter tracked wall clock, a deliberate reset the counter detected, and for pyOCD the additional halted-session control in which the same counter froze, which is what makes it an admissible witness rather than an untested instrument. Every read log carried the least-intrusive connect verbatim (`mode=HOTPLUG` with no `reset=`; `--connect attach` with nothing that halts). The two code comments that said documented-is-not-measured cite the evidence on their issues now, and `examples/nucleo-f446re_demo` carries the witness itself, a 1 ms SysTick counter `uptime_ms`, so re-running either proof on any bench starts at `flash_firmware` instead of at writing firmware. The pyOCD measurement also exercised the atomic backend switch in production for the first time: `debuggers.<name>.type` to `pyocd` with `executable: null` in one call. (#348, #349)

- **Nobody could tell this bench which GDB reads its images.** The generated configuration carries `debug.gdb_executable: null` whenever the shell that generated it had no GDB of its own, and there was no sanctioned way back into the key afterwards: `project_config_set` refused it as a key outside its closed set, `adopt-hardware` carried probe identity only, and no grant applied to it. The runtime fallback covers the ordinary case, resolving `arm-none-eabi-gdb`, `gdb-multiarch` and `gdb` on the PATH the server was started with, and it is what the bench that reported this leaned on, because STM32CubeCLT's GDB could be put on the spawning environment's PATH. An operator whose GDB lives anywhere else was sent to hand-edit the authoritative file, which is the one move the field-wise write path exists to end. Which GDB reads this bench's images is a description of this bench, the same class of fact as `debuggers.<name>.executable`: a toolchain on this host, at a location only this host can state, granting nothing the debug permissions beside it do not already decide. So the key joins the settable description keys behind `allow_config_description_write`, with the plumbing the four debugger fields established, and its value is held to the rule every configured executable is held to by the loader rather than by a second copy of that rule: a path that is missing, that is not a single-link regular file, or that sits under `workspace_root` is refused as `config_invalid` naming `debug.gdb_executable`, and the file that was there stands untouched. `debug` is now the one section with a key on each side of the split, `gdb_executable` describing the bench and `allow_all_symbols` granting something, and the key model tells the two apart by field so each answers to its own right. A refused load also keeps the loader's own sentence in front of the rollback's now: for a key whose whole validation is the loader's, a field name on its own never said whether the path was missing, a hard link, or inside the workspace. `adopt-hardware` fills the key in as well, from the same candidates in the same order, reported under the plan the way the backend's executable is: carried when the document has nothing there, `kept` with both values when somebody chose a GDB, `already_current` on a second run, and absent from the plan entirely on a host that has none. Generation writes what that same lookup found, so adoption on a freshly generated file still has nothing to carry, and the file names its GDB instead of depending on whatever PATH the server is next started from. (#355)

### Fixed

- **The bench wrote down a `state_root` it would then refuse, and refusing it locked the door on the way out.** On a Windows 11 profile whose agent host runs inside an MSIX AppContainer, `agentic-hil init` and `project_config_create` wrote `state_root: C:\Users\<u>\AppData\Local\agentic-hil`, and every hardware action afterwards came back `audit_unavailable` carrying `unsafe_configured_path` on `.../reports/report-state.json`. The container virtualizes `%APPDATA%` and `%LOCALAPPDATA%`, so a path under either creates, opens and writes exactly as it reads while resolving onto the package's private `LocalCache` tree, and two checks that were each right about their own question disagreed about one directory: `safe_writable_directory`, which generation selected on, accepted it because it really is creatable and really is writable, and `safe_file_path`, which every write in the package passes through, refused every file under it because the parent does not resolve to itself. `provisionable_state_root`'s own comment already claimed the invariant it was missing, that selection applies the same test a later write will apply. It applies it now, so a spelling the enforcer will refuse is never written down and the `~/.agentic-hil` fallback engages exactly as it was designed to, and the refusal carries `resolved_parent` beside `path`, because the configured spelling is the one that looks clean and the resolved one is the answer. The second half was the worse half. `project_config_create` is itself audited, and the audit check writes under the very `state_root` that is broken, so the broken root guarded the one call that replaces it and the bench could not regenerate its way out; `state_root` is not in `project_config_set`'s closed key set and adoption does not carry it, which left hand-editing the authoritative file as the only route, and that is the one thing the doctrine forbids. Generation is exempt from that gate now, at the service and inside the shared discovery, and it takes the route the first `init` of a workspace takes: the machine-wide enumeration lock and `probe:<serial>` are still held for the read, so no board another owner is on is connected to, and the result reports that the read went unaudited and why, instead of leaving an operator to infer it from a record that is not there. (#353)

- **The same bench could not put a configuration anywhere at all, and the refusal sent whoever debugged it after a symlink that was not there.** `project_config_directory()` derives `%APPDATA%\agentic-hil\projects`, the per-workspace directory under it is created, and the sidecar lock write is then refused with `unsafe_configured_path`, because what a packaged host creates under Roaming resolves into its private `LocalCache` tree. So `project_config_create` and `agentic-hil init` dead-ended on a stock installation inside any MSIX-packaged host, and the refusal's own remediation named `~/.agentic-hil` as a safe answer that no code path took: `AGENTIC_HIL_CONFIG` pointed at the resolve-stable spelling was the only way through, and that is not a lever a stranger finds. `state_root` had learned the candidate walk and the configuration's own location had not, so it has it now, in the same order and on the same terms: the platform default first, then `~/.agentic-hil/projects`, and a root that already holds this workspace's configuration ahead of both, so a file that is in force is never answered around and `project_config_set` cannot end up refusing every write as not this workspace's authoritative file. Discovery walks the same list, or a fall-through would write a configuration nothing could load again, and so do the projects listing, the agent rule refresh and `uninstall`, or a configuration generated under the fallback root would be found by nothing on disk. The refusal misled as badly as it dead-ended. It said to replace the symlink with a real directory and carried no `component`, while the chain shows no symlink, no reparse point, link count 1 everywhere, and `samestat` holding, because the indirection lives in name resolution alone; whoever debugs that walks the chain, finds it clean and is stuck. The two conditions behind that one sentence are separate refusals now, the parent-resolves-elsewhere one carries `resolved_parent`, the spelling it compared against and the one that works, and the remediation reads that first and says not to go looking for a link that is not there. The symlink wording stays where a symlink is what is actually there, and it now names where the link goes. (#354)

## [0.19.0] - 2026-08-30

### Added

- **A bench behind a TLS-inspecting proxy is a container anyone can run now, instead of an error message only the operator sitting behind that proxy could reproduce.** On such a machine `agentic-hil upgrade` ends with `invalid peer certificate: UnknownIssuer` while curl, apt and the browser on the same host keep working, because uv checks the chain against roots compiled into its own binary and the proxy's CA lives in the machine's own store instead. Reporting that has meant pasting five lines of uv output and asking people to take them on trust: nobody without a corporate proxy could get behind the failure, and nobody could tell from the paste whether the machine's store, the proxy or the package was at fault. `evals/tls_proxy/` builds the bench from nothing. One image starts mitmdump as an ordinary HTTP(S) proxy on loopback, mints its CA at build time and installs it with `update-ca-certificates` so the machine trusts the proxy, exports `HTTP_PROXY` and `HTTPS_PROXY` for every program in the image, and fetches uv before any of that is in the environment. The entrypoint then plays the whole scenario in order and stops at the first step that fails. The seed installs 0.16.0 with `UV_SYSTEM_CERTS=1` set for that one command, which both provisions the bench and proves the system-store path works at all. Proof 1 runs `agentic-hil upgrade --json` with the variable removed from the environment and asserts the report carries `upgrade_failed` and that the manager stderr it recorded holds both `invalid peer certificate` and `UnknownIssuer`. Proof 2 is the upgrade in this checkout run on the same bench: a tool environment is provisioned by name and unpinned so `uv tool upgrade` reaches the index and meets the same failure, this working tree's package is overlaid onto it so the code under review is what runs, and then `agentic-hil upgrade --json` runs with the variable removed and the run reads the retry off the report, the first attempt carrying the trust failure and the second, with `UV_SYSTEM_CERTS=1` added, the one that gets through with verification on. Proof 3 runs the released one-line installer exactly as it is typed, `curl -LsSf https://github.com/agentic-hil/agentic-hil/releases/latest/download/install.sh | sh`, and asserts that it met the same failure, said it was switching to this machine's own store, exited zero and left the current release answering `--version`. Every step prints its whole output before its verdict, and every verdict is a PASS or FAIL line with the decisive evidence line under it, so the container is the report rather than something a reader has to summarise afterwards. Nothing in it relaxes verification: both attempts a run makes check the chain and only the store changes between them, the CA is minted inside the image and its key never leaves it, and a test asserts that no spelling of `--insecure`, `--trusted-host` or `SSL_CERT_FILE` ever appears in either committed file. Nothing it installs is a moving download either: the base image is pinned by digest and the uv bootstrap is pinned to the version and checked against the hash `install.sh` already carries, which is both the refusal that file makes and what lets two runs of the eval be compared at all, and Dependabot has an entry for the new container directory because the docker ecosystem reads one directory per entry and a digest nothing moves is a stale image rather than a safe one. The build and the run are wired into pytest behind two gates, Docker being present and `AGENTIC_HIL_TLS_PROXY_EVAL` being set on purpose, so an ordinary suite run skips them with a reason that names the variable and default CI never spends the network or the minutes; the static half of that file reads the committed files and runs everywhere. Two commands now hand the whole scenario to anyone: `docker build --file evals/tls_proxy/container/Dockerfile --tag agentic-hil-tls-proxy-eval:local .` and `docker run --rm agentic-hil-tls-proxy-eval:local`. #326 taught `agentic-hil upgrade` the retry the installer already makes, and it is pinned two ways: `tests/test_upgrade_certificates.py` stubs the manager and runs everywhere without Docker, and proof 2 runs the real thing on the live bench, overlaying this checkout onto a by-name install so the retry meets real uv, a real child environment and the machine's own store rather than waiting for a release to carry it. Proof 1's seed stays 0.16.0 on purpose, the failure an operator on that release still meets, and proof 3 shows the released installer is their way through it. (#326)

- **This bench refused its first flash after every power-up and took the retry, and nothing in the configuration could say why.** The erase failed, the very next call succeeded with the same image, and five occurrences landed within 9 ms of each other, which is a core executing from flash interfering with the erase of the memory it is running out of rather than anything that varies with the artifact or the load. Halting the target first is no answer on this interface: STM32CubeProgrammer reboots the target on every invocation of the CLI (a SysTick counter read twice across two invocations jumped backwards), so a halt from an earlier call has never survived into the flash call, and the connect the flash made was hard-coded to `mode=HOTPLUG`, which leaves the core running through the erase. `debuggers.<name>.connect_mode` now says it once instead: `under_reset` makes the flash connect with STM32CubeProgrammer's `mode=UR` and hold the target in reset while the probe attaches, so the core never runs during the erase, and `hotplug` is the default, so a file that does not name the key flashes exactly as it always has. The spelling is the CLI's own, taken from its `--connect` usage text ("Connection mode. Value in {UR/HOTPLUG/NORMAL/POWERDOWN/HWRSTPULSE}") rather than assumed, and so is the consequence written beside it, "Reset mode with UR connection mode is HWrst", which is why the setting needs the probe's reset line wired to NRST, as an on-board ST-Link has. It is read by `flash_firmware` and by nothing else, so `debuggers.<name>.connect_mode` decides how a flash connects and touches no other call: `probe_target` stays hot plug because it is the least intrusive call here and erases nothing, the typed memory reads take their own hot-plug connect so reading a symbol never resets the board (#342), and `reset_target` keeps the NORMAL connect its own operation decides. It is settable behind `allow_config_description_write` beside `probe_id`, `executable`, `interface_cfg` and `target_cfg`, because it grants nothing, both of its values being a flash the configuration already allows. Only the ST-Link backend can carry it out, so `openocd` and `pyocd` refuse `under_reset` at load, naming the field, the value they do accept and where the same effect lives for them (OpenOCD's own scripts), rather than reading a word and ignoring it. (#329)

- **Every upgrade that fails now says what to do about it, not only the one that met a proxy.** `upgrade_failed` is where every upgrade that stops without replacing anything lands, and the type had no `ERROR_CATALOGUE` entry, so its refusal rendered Details and whatever `next_steps` the producing code had attached. Only the certificate path attached any, because #326 had to work around the gap with `next_steps` while `knowledge.py` was outside its scope. An index that could not be reached, a resolver with no solution, a package manager that is no longer where it was, a release withdrawn between the resolution and the download: all of them went out with no What-to-do section at all, next to `installation_broken` and `upgrade_blocked_by_pin`, which each carry one. The entry says what the type means, including that the previous installation was measured to still load rather than assumed to, and it names the four causes; its steps read the manager's own words in `install.stderr` first, or `exception_type` and `detail` when the manager could not be run at all, then the conditional `certificates` clause, which points at the export or the CA install that `next_steps` names when the failure was a proxy, then running the upgrade again, and last the one-line installer as the repair path, which on a machine that already has an installation goes through the package manager again and repairs in place. `do_not` names the four wrong turns: reporting a working bench as broken, reaching for a switch that turns verification off, clearing the environment before the next attempt, and `sudo pip` or `--break-system-packages` on a distribution-owned Python. The remediation is merged into the result itself rather than left to the renderer's catalogue lookup, because an MCP caller reads the document and acts out of `remediation`. The standing proxy remedy is not made an unconditional step: the catalogue names the CA only through its conditional `certificates` clause, so a failure that met no proxy is never told to touch a trust store, and the imperative itself stays a measured `next_step` attached only on a run that met one. That is what keeps it on `installation_broken` behind a proxy too, whose own entry says nothing about certificates and whose operator has a repair command to run back through the same proxy. A step an outcome's own remediation already carries is dropped at the merge rather than printed twice, under both What to do and Next steps. What stays on the result is the part a catalogue cannot know: the variable, the value or the bundle measured on this host. (#332)
- **The ST-Link backend answers all three typed-debug reads now, and the two that touch the board stopped resetting it on the way in.** A bench on 0.18.0 with an ST-LINK V3SET wanted a coverage dump, RAM-resident measurement data read before a run ends, and met both halves of one mistake. `debug_symbol_info` refused outright, although where a symbol is and how large it is are properties of the image and the image is on disk: that call never needed a probe at all, and refused only because it was filed with the session family. It is served now through the resolution the two memory reads already run before they connect, the ELF a confirmed `flash_firmware` put on the board, copied into a private file and hashed against the flashed digest so the symbol table provably describes what is on the target, queried with a GDB that is handed no `target` command and can therefore reach no probe even if one is plugged in. The result is the OpenOCD path's, field for field and summary for summary, plus the `symbol_source` naming the image that answered, and it reports `target_contacted: false` rather than leaving a reader to infer it: no probe is opened, so no debugger lease is taken and no programmer log is written. The second half mattered more. `debug_symbol_value` and `debug_dump_symbol_ihex` shipped connecting with `mode=NORMAL`, STM32CubeProgrammer's own default and a connect that resets: its `--connect` usage prints "Connection mode. Value in {UR/HOTPLUG/NORMAL/POWERDOWN/HWRSTPULSE}" with "default mode: NORMAL", and beside it "Reset modes: SWrst/HWrst/Crst. Default mode: SWrst", and #329 measured what that costs on this interface when a SysTick counter read across two invocations jumped backwards. A read that resets the target destroys the RAM it was asked for and answers with a freshly reset board's bytes, which is precisely the measurement a coverage dump exists to take. Both reads now send `mode=HOTPLUG` and no `reset=` option at all. The evidence is the CLI's own words rather than an assumption about what "hot plug" ought to mean: it prints "Device connected in HotPlug mode, a Reset is needed to program the flash", which is the programmer stating that its connect did not perform one, and it advises "The suggested connect mode while using the -regdump command is hotplug" for the one command it ships that only reads. Both strings live in `STM32_Programmer_CLI.exe` v2.23.0 and can be re-read from any installed copy; ST's UM2237 is where the modes are defined and defines hot plug the same way. What is documented is not what is measured, and nothing here claims otherwise: this encodes the least intrusive connect the CLI documents, strictly less intrusive than the connect it replaces, and no result carries a claim of proven non-intrusiveness, which is a bench measurement belonging to the operator and to the issue. `debuggers.<name>.connect_mode` still does not reach the reads and now must not more than ever, because `mode=UR` holds the target in reset and RAM read through a held reset line is not a measurement of anything the firmware did; a test asserts the flash under reset and both reads hot plug out of one configuration, and the read argv is pinned negatively as well as positively, because a connect that quietly went back to resetting would break nothing a positive assertion sees. (#342)
- **This bench had to leave MCP to say which debug stack it runs.** Moving the `dut` probe from the CubeProgrammer backend to OpenOCD meant opening `config.yaml` in an editor: `debuggers.<name>.type` was deliberately absent from the keys `project_config_set` writes, while `executable`, `interface_cfg` and `target_cfg`, the three fields that between them fully determine which binary runs with which scripts, were all open behind `allow_config_description_write`. The reason recorded beside the exclusion was that `type` changes what a call does to the board rather than what the board is, and that reason does not survive next to those three: an operator who grants description-write has already handed over what reaches this board, and which debug stack a bench runs is a description of that bench, learned the way every other description here is learned, from the hardware in front of somebody. So `type` joins its siblings under the same grant, and the half of the old rule that does stand on its own merits is now written down as itself: `flash_address` decides where an image lands, `resource_id` renames the lock a run takes, `timeout_s` decides when a call is abandoned mid-operation, and the COM buffer limits and DTR/RTS lines decide how much of a line is read and whether opening a port restarts the target, so each of those stays locked because it changes a call while describing nothing. What keeps the switch honest is validation rather than a lock, because `type` is the one description key whose value decides which *other* fields its entry needs: a change naming a backend the entry is not equipped for is refused before anything is written and names exactly the keys that are missing, so an entry moving to `openocd` without `interface_cfg` and `target_cfg` is refused rather than left to load on those fields' schema defaults and then reach the board through whatever they resolve to on this host, and the same keys sent in one call land the whole entry. Only fields this surface can write are demanded: `interface` on stlink and `target_type` on pyocd are required by their backends and are not keys `project_config_set` sets, so demanding them would have made those two switches impossible rather than atomic, and both have a working unset behaviour the backend field matrix states. The other half of a half switch, a field the new backend refuses rather than requires, stays where that rule already lives: `connect_mode: under_reset` switched onto `openocd` is refused by the loader as `config_invalid` and the file that was there stands untouched, so `connect_mode: hotplug` in the same call is what makes that switch land. `project_config_adopt_hardware` still will not carry a `type`, because a probe hands you an identity and never a choice of debug stack, but its refusal now names the call that does change one instead of sending the operator back to the file. (#343)

- **A bench on `type: pyocd` could not read a value out of its own target, and the reason it was given was that the measurement had not been made yet.** pyOCD reads memory perfectly well, so refusing `debug_symbol_info`, `debug_symbol_value` and `debug_dump_symbol_ihex` there was wider than the hardware's own limits, in a way the ST-Link backend's refusal had already stopped being (#342). What stood in the way was not the command but the connect: pyOCD has four connect modes and three of them touch the core, and a read taken under the wrong one hands back a halted or freshly reset board's bytes and calls it a measurement. pyOCD says which is which, in three places that agree. Its command line lists them (`--connect MODE`, "Select connect mode from one of (halt, pre-reset, under-reset, attach)"); its user documentation gives each one a sentence, of which one is "'attach': connect to a running target without halting cores" while the other three halt, reset before connecting, or hold reset asserted; and its own connect sequence does nothing at all under `attach`, the halt step opening with a test for that mode before it halts anything. So the two reads that reach the board now run `pyocd commander --connect attach --command "savemem ADDR LEN FILE"`, with the mode written on the command line rather than left to the commander's default, because a default is a decision a `--halt`, a project's own `pyocd.yaml` or a later release could change without anything in the log saying so. What is documented is not what is measured, and nothing in a result claims otherwise: this is the least intrusive connect pyOCD documents, and the proof that a read leaves a running core untouched is a bench measurement that belongs to the operator. `debug_symbol_info` needed no probe on any backend, an address and a size being properties of the image, and it now answers on both backends without one, out of the same digest-verified copy of the ELF a confirmed `flash_firmware` put on the board, with the same fields, the same summary and the same refusals, so a plan that reads a counter no longer has to know which probe it is running on. The dump ends differently here than on ST-Link because `savemem` writes a raw binary: the Intel HEX a caller was promised is written by this server from the bytes it read, so the path a caller named never reaches pyOCD at all. A read that completed and left no bytes is a failed read rather than an empty answer, and a pyOCD failure during one is now reported as a failed memory read with its own causes instead of as an unknown debugger error. `debuggers.<name>.connect_mode` reaches none of this and could not: this backend refuses `under_reset` when the file is loaded, and RAM read through a held reset line is not a measurement of anything the firmware did. (#344)
- **A bench could read a value out of its target and could not write that read into a test plan.** `debug_symbol_value` and `debug_dump_symbol_ihex` have answered on `type: stlink` since 0.18.0, and since #342 they answer without resetting the board on the way in, which is exactly what the workflow that asked for them needs: dump RAM-resident measurement data before a run ends. The test reactor admitted `dump_memory` and `read_symbol` steps only where the configured debugger was `type: openocd`, so the same read was available by hand and refused as a plan step, with "Typed debug actions currently require a debugger of type 'openocd'" and not a word about the read that works on that very probe. A plan may now carry both steps with no `debug_start` before them wherever the backend serves those reads with no session behind it. Nothing is inserted into the plan and nothing is invented: there is no session on such a bench for the step to be inside, so the step goes to the same standalone read a hand-made tool call makes, on its own one-shot probe lease, held to the same `debug.allowed_symbols` and the same `debug.max_dump_size_bytes` it has always been held to. Which benches those are is derived from what the backend implements rather than from a list of type names. One place answers "does this backend serve these reads with no session": the coordination layer asks it to decide whether a read takes its own lease or runs on a session's, and the reactor asks the same place whether a plan needs a `debug_start` step at all, so a lease class and a plan gate cannot come apart, and a backend that gains the ability serves these plans with nothing in the plan format or the reactor to change, which is precisely what happened in this same release when the pyOCD reads arrived (#344). An action counts as one of them exactly when the tool it calls is one the backend serves that way, so there is no second list of actions to keep in step either. Inside a debug session nothing moved: on OpenOCD both steps still run in the session the plan opened, on that session's lease, a read outside one is still refused there with the sentence that says opening one is the fix, and `run_until_breakpoint` and the session lifecycle still require the backend that has a session. The combination that remains unsupported is refused before the run and by name rather than as a schema error: the backend, the step and its number, which reads that backend does serve, and the configuration change that would run it, quoted from the same table the tools' own `not_supported` refusals use, so a plan author and a tool caller are never sent two different ways out. The plan contract, the plan schema's own step descriptions, the testing guide and TROUBLESHOOTING's backend-refusal section all say which steps need a session on which backend, and why. (#345)

### Changed

- **A failure carries its diagnosis, and until now exactly one of them did.** #327 attached `programmer_output` to the erase refusal because the line that justified the classification survived nowhere else in the result: the transcript sat in the log file the result names by path, so an agent relaying the result to a person relayed every fact except the decisive one. Every other classified failure still shipped without it. A failed download, a verify mismatch, an internal command error and a reset failure all carried a classification, a summary and a list of likely causes, and left the sentence all three were derived from on disk. The capture now travels with every classified failure on all three backends, in the same nested shape #327 chose: `returncode`, `stdout` and `stderr` under `programmer_output` on the result. Nothing else had to move for it, because the human rendering already prints a member named `stdout` or `stderr` as a literal block at any depth (#314) and the stream redaction already covers those key names at any depth (#317), so both surfaces came for free. The machine document carries the capture whole and the renderer's caps decide how much of it a person reads, which is how the erase refusal has done it since #327: truncating at capture time would put a shorter transcript in the report than in the log file the same result names. The two backend erase entries now send the reader to `programmer_output` first rather than to a log path, because the transcript arrived on the result. Two exemptions, both deliberate and both pinned by tests. A timeout keeps carrying nothing, because a killed process says nothing about where it stopped and returns before anything is classified, and a success does not grow the field, because attaching the capture there would put a copy of every transcript this bench produces into every report it writes. (#334)

### Fixed

- **A bench behind a TLS-inspecting proxy could install Agentic HIL and then not upgrade it, and was handed a certificate chain instead of the remedy.** `agentic-hil upgrade` there got five `Caused by:` lines out of uv ending in `invalid peer certificate: UnknownIssuer`, and answered "Agentic HIL package manager reported an upgrade failure" and stopped. That signature is the one `trust_failure()` in `install.sh` has recognised since #293, where the installer retries the manager once against this machine's own certificate store and says so while it does it, which is why the install on that same bench had worked; the upgrade runs the same managers against the same index and did neither, so the operator was left to read their own chain and re-derive a remedy this project already encodes. A manager that exits non-zero with one of those signatures in its own words is now run a second time with this machine's store in reach: `UV_SYSTEM_CERTS=1` for uv, and for pip and pipx the first readable bundle of the list `system_cert_bundle()` walks, as `PIP_CERT`. Once, only on that signature, only in the child's environment (`os.environ` is never written, so nothing else this run starts is changed), and with verification on in both attempts; no path through it reaches `--allow-insecure-host`, `--trusted-host` or any other switch that turns checking off. A variable the operator exported already is theirs and is neither overridden nor repeated, because it was in force for the attempt that just failed, and the result says that instead of pretending to retry, which is also the answer on a host where pip has no bundle file to be pointed at, Windows included. Every result of a run that met a proxy says what was tried: a success names the store that made it work, so the operator learns why it needed one, and the refusal after both attempts names the cause, carries the first attempt's own words under `install.certificate_retry.first_attempt` beside the second's so the decisive `Caused by` line reaches the terminal without `--json`, and points at installing the proxy's CA and at the standing `UV_SYSTEM_CERTS` export TROUBLESHOOTING.md recommends. A failure that names no certificate is run once and reported once, exactly as before. - **Under `--allow-dirty`, a stalled round's work moved onto a pathname that was already dirty vanished from the guard that stops a clean exit over it.** Outstanding work that moves is carried by `present_dirty - inherited_dirty`, the paths dirty now that the round did not start with, and that subtraction assumes a move's destination was not already dirty when the round began. The first identity is the inode, and it is the one that holds when the round does not merely move the file but edits it after: a move on one filesystem carries the outstanding object's inode onto its new name, and a truncating write in place reuses that same inode rather than making a new one, so a round that moves the stall onto inherited dirt and then adds a line to it is followed by the inode when its bytes, the thing a content match reads, are no longer what the round began with. The rename map still carries every case where the ground was clean, and identity is only the tie-breaker where names lie. A path that is gone carries none either way; a directory and an empty file, which a content match had to leave out because every empty file's bytes are every other's, carry the inode that is theirs alone, so a stall emptied after a move is followed rather than lost. An atomic save reaches past both identities at once, though: write the edited bytes to a temporary file and rename it over the destination, and the inherited dirty name the stall moved onto takes the temp file's inode and the temp file's bytes, so the inode a move would carry is gone and the content a move would keep is gone with it, the ordinary way an editor or formatter writes a file, and how the two-round scenario slips the guard again when the round both moves the stall and saves over it. Where the identities the object carries have run out, an atomic save writes the edited bytes to a temporary file and renames it over the inherited dirty name, so the inode a move would carry and the content a move would keep are both gone, no proof taken at a pathname can stand in for them, and none is asked. A `git commit` leaves the work tree untouched, so it is tempting to read an object still sitting at its followed name with the inode and bytes it began with as reviewed; but an inode is no one file's alone, and a hard-linked alias can carry the stall's original inode and original bytes back onto the followed name itself while the edited work is atomic-saved onto inherited dirt, and a round that simply writes that work into the inherited dirty file in place needs no alias at all. So whenever a followed name vanished, every inherited dirty path this round rewrote is kept, a move onto inherited dirt always rewriting its destination and a false stall the operator clears by committing being the safe error where a false clean exits 0 over work no review read. The content is still named the way git names its own commit, the path's clean filters applied and the repository's object format used, so a `core.autocrlf` rewrite or a sha256 repository does not read a line-ending-only change to inherited dirt as a rewrite and cost a false stall there. The narrower inode and content identities above still carry every move they can name; this retains only the moves they cannot, at the cost of stopping as stalled the round that commits the stall under its own name and edits the operator's file beside it, indistinguishable, at exit, from that same edit hiding round 1's work, and left in the tree for the operator to commit or clear. - Two test reactor step actions, `reset` and `uart_expect`. `reset` drives the same `reset_target` path the MCP tool does and takes the same modes — `run`, `halt`, `init` — so a backend that will not run one refuses the step with its own `not_supported` rather than a reworded approximation of it; preflight refuses the step without `allow_reset` on the named probe, and inside a live debug session, where a `reset_target` one-shot could only ever come back busy. `uart_expect` takes a required `text` and a required positive `timeout_s` and waits for that substring on a serial line the plan has already opened, reading through `com_read` and matching against everything read so far, so a banner that arrives in pieces still counts. A step whose text never appears fails the run with `uart_expect_timeout` carrying the last 512 bytes the port did send, decoded, so a silent board and a wrong banner read differently.
- `examples/nucleo-f446re_demo/testconfig.yaml`: the demo loop — flash, open the port, reset, expect `Hello World`, close — as a declarative plan, run from that directory with `agentic-hil test-reactor --test-config testconfig.yaml`.

- **Configuration version 3, under which a `com_ports` entry must say which hardware it is.** `serial_number`, `vid` and `pid` have shipped beside `device` for two releases, `adopt-hardware` and `init` write them, and `doctor` warns about an entry that carries none of them — but a warning is not a property of the file, and a bench nobody runs `doctor` on keeps identifying a board by an enumeration order, which is the exact defect `serial_number` was added for. Under `version: 3` an entry carrying a `serial_number`, a `resource_id` or a `/dev/serial/by-id/...` device name is identified and needs nothing more; an entry carrying none of those must declare what does identify it, in the new key `com_ports.<name>.identity_source` — `vid_pid` (or `vid`/`pid`) for an adapter that publishes USB ids but no serial number, `device` for one that publishes neither. A version 3 file with an entry that has neither an identity nor a declaration is refused at load, naming the entry, its `device`, its `actual_identity_source`, and `agentic-hil adopt-hardware --apply`. The rule is decidable from the document alone, which is what makes it a version rule rather than a host check: a configuration is read on machines with nothing attached, so a check that needed the hardware present would refuse a bench for being unplugged — the file carries the answer instead, and the deliberate exception is visible in it rather than reported at runtime. The declaration grants nothing and identifies nothing on its own: one that disagrees with the entry's own keys (`identity_source: serial_number` where there is no serial) is refused at every version, so version 3 cannot be satisfied by writing something untrue. `adopt-hardware` writes whichever of the three the attached adapter turns out to justify — it has just asked the adapter, and "this adapter publishes no serial number" and "nobody filled it in" are otherwise the same file — and corrects a declaration that has stopped being true, which is the case a port swapped for one that does publish a serial would otherwise leave unloadable. Versions 1 and 2 keep loading exactly as they do today, warning included; the loader accepts 1, 2 and 3, and nothing is inferred from the absence of a key, so an update adds this requirement to a file that opted into it and to no other. Migrating is one edit in one order, because `adopt-hardware` loads this configuration and therefore needs it to load: run it with the boards attached while the file still says `version: 2`, then set `version: 3`. `agentic-hil init` and `project_config_create` write version 3, and the shipped schema, the generated file's own comments, the MCP configuration reference, `README.md`, `TROUBLESHOOTING.md` and `docs/security-design.md` state the rule and the migration. (#144)

- **An effect tool called with no run open wraps itself in an implicit single-action run.** Run semantics — declare, audit, abort, recover — apply to every effectful interaction, whether it is one action or fifty; a declared run is only the explicit spelling. Until now a bare `com_write`, `can_send`, `flash_firmware`, `reset_target` or `probe_target` from an agent doing one thing sat outside the model entirely: it took its lease, and if it failed into an incident there was no run teardown to hang a recovery action on, so the only route back was `hardware_recover` or a person at a shell — while the identical call between `bench_run_start` and `bench_run_stop` recovered itself. The call now declares the run, over exactly the resources it is about to lease, through the same `begin_run` an agent's own `bench_run_start` makes: the same hold, the same lease record, the same audit trail. The teardown is the same too — shared with `bench_run_stop` rather than copied beside it — so an incident left standing when the devices go back aborts into `recover_after_failed_run` exactly as a declared run's would, and the result carries the same `recovery` block naming the actions and the outcome. The report says which kind of run it was: a `run` block with `implicit: true`, the declared devices, the `implicit:<tool>` label and whether the run aborted, because "this call ran in a run" and "an agent declared a run around this call" are different facts and an operator reading the report afterwards has to be able to tell them apart. No test plan is required for one action, and nothing changes for a call inside a declared run: that run already holds everything, spans more than one call, and keeps its own boundary and its own teardown — a failure mid-run still recovers at `bench_run_stop` and not a step earlier. The wrap lives at the dispatch layer, at the one place every tool passes through, so it is never something a tool has to remember to do. The wrapped set is derived rather than listed — the tools whose failure can raise an incident, less the read-only ones (a read leaves nothing to put back), the session starts (their hold outlives the call, so a run around one would release a session that is still open), the calls made through an open debug session (a recovery action reaps this owner's debugger processes, so such a run would take the session with it; `debug_stop_session` and the containment tools beside it are that teardown), and the two configuration tools, which refuse while a run holds the bench and would therefore refuse themselves. A tool added to the incident-marking set later joins this one with it instead of being silently left outside the run model. The wrap also stands aside while an incident is standing: a new run is the stimulus class and waits for it, while the recovery class must reach the board through it, and wrapping either in a run it could not open would rebuild the padlock. (#147)

### Changed

- **The two debugger permissions that withhold flashing now say why.** `allow_raw_debugger_commands` and `allow_mass_erase` are generated false, and every document that explained the pair restated the rule — "validated flashing and unrestricted debugger access are mutually exclusive policies" — rather than giving it. ### Fixed

- **A run declaration mixing device objects with hand-written resource names is refused instead of half locked.** `bench_run_start` accepts either form, and the acquisition chose its branch on whether any device object was present: one device sent the whole declaration down the device branch, so every bare name beside it was never taken — while the declared set covered both, and the run reported the named board as held for its whole length. A foreign holder could take that board while the run counted it as its own, which is invisible from inside the run and is the outcome the device path was built to prevent. The mixed form is now refused with `invalid_argument` before anything is locked, naming both halves of the declaration (`device_lock_keys`, `declared_resource_names`) so the caller can see which one it wrote. Neither homogeneous form changes: a declaration of devices is resolved, collapsed and taken exactly as before, and one of bare names is locked exactly as before. No caller passes the mixed form — every one of them hands over a device set or a list of names — so this closes a boundary rather than removing a capability. (#140)

- **`agentic-hil init --force` refuses while a run holds any configured device.** Every other write of the authoritative configuration already refused one — `project_config_create`, `project_config_adopt_hardware` and `agentic-hil grant`/`revoke` all answer while a run, a lease or another terminal holds the bench — and the regeneration had none. What stopped it was incidental: a run that declared the probe owns the lock the board read takes between enumerating and connecting, so the read answered `device_busy`. A run that declared only a COM port or only a CAN bus holds no probe, so nothing stood in the way and the whole file was replaced — permissions, baudrate, bitrate and device bindings — underneath live measurements taken under the policy it had just discarded. `init --force` now asks `bench_open_holds`, the same question the permission commands ask, and answers `config_write_in_open_run` with `open_holds`, `retry_safe: true` and a next step naming `agentic-hil lease-status` for the holder, which is usually another process. The refusal is raised before the board is read, so a `--force` typed by accident during somebody's run costs neither a HOTPLUG connect nor a line in the audit trail, and it is refused as what it is rather than as a busy device. A workspace with no loadable configuration names no devices and is unaffected: the first `init` of a workspace still goes through, for the same reason it still reads the board without a lease. (#138)

- **`tools/ci_linux.py` reported success for a run in which no test executed.** It forwarded whatever the container exited with and asserted nothing about what ran, and it was observed exiting 0 after zero tests were collected: the clone inside the container borrowed objects through `.git/objects/info/alternates` at a path the container could not resolve, so it never built a usable tree, and a green result came back for work that never happened. The clone step now reports its own failure as itself — the script checks the clone rather than relying on `set -e` alone, and checks that what it produced is this repository — so a run that dies there goes red naming the clone instead of surfacing as a pytest step that never happened. The run is then held against pytest's own summary line: its absence is a failure, and a summary accounting for no tests at all is a failure too, because zero collected is never a success of this tool. A failing suite still leaves the process with pytest's exit status, and a selection that legitimately only skips still passes — the floor is on what pytest found, not on what it chose to execute. (#139)
- **The hardware evaluation's MCP probe read its tool contract from a file that does not exist.** `evals/hil/mcp_probe.py` looked for `tools.list.expected` in its own directory; the repository's one copy is `evals/install/tools.list.expected`, the file the shipped tool tables are already held against in both directions. The comparison the probe exists for therefore raised `FileNotFoundError` every time instead of running, unnoticed because nothing in the suite covered `evals/hil/` and that evaluation only runs against attached hardware. The probe now reads the existing contract rather than gaining a second copy to drift against, and reads it before the server is started, so a contract it cannot find is reported without leaving a process behind. `evals/hil/` is no longer entirely without coverage: the probe is driven end to end against a stand-in server, which is enough to reach the comparison and watch it report tool-surface differences. (#145)

- **A CAN bridge that opened its channel and then failed no longer reports that the bus was never touched.** A bridge's own `ok: false` on `open` was one case and is now two. The one that has always been right stays exactly as it was: a clean refusal — a mistyped channel, `open` failing before anything was opened, by far the most common bridge failure — keeps `side_effect_committed: false`, `side_effect_status: not_started` and `retry_safe: true`, because that is a bad configuration and not a bench incident. The one that was wrong is the bridge that opened its channel and then failed at a later step of its own initialization: it is sitting on the bus, ACKing, while it reports the failure in the first person, and the result said the session never started. That case now withholds the marker and reads `side_effect_status: unknown`, which is what the direct-adapter path has given a post-contact failure since the marker existed. Protocol v2 is one request and one response, so nothing in the envelope distinguishes the two — the error type names what went wrong, not when, and it is a string the bridge chose — so the bridge is asked to say it: `channel_open: true` on its own error response means the channel was up when the step that failed ran. A field on the error response and not a version bump, the same way `listen_only` was added to the success response, so a bridge that does not set it is unaffected in either direction. Only a literal `true` moves it; absent, `false`, or any truthy stand-in leaves the refusal, because the field can only ever widen an unknown and a typo in somebody else's bridge must not take a bench out of service. The lease still comes back in both halves — the bridge is closed and the close confirmed — so what changed is what the report claims and not whether an operator is sent to a bench. Two neighbours went with it: the adoption refusal after a failed lease release rendered a discovery that set no side-effect marker as the positive claim that nothing was committed, where absence means unknown and now says so; and a success predicate's test fixture asserted over a `side_effect_status` value no production path emits. (#141)

- **`invalid_argument` carries a way forward, and two numeric conversions answer instead of raising.** The error catalogue covered forty refusals and not the most frequent one this server produces: `remediation_fields("invalid_argument")` returned nothing, so the refusal a caller meets most often went out with no next step and no `do_not` line while `permission_denied`, `device_busy` and `com_port_identity_mismatch` each carried one. The new entry is about the fields the result already carries — how to read `field`, `validator`, `allowed_values` and `value` — rather than about any one argument, because a per-argument entry would be a second copy of the input schemas with nothing keeping it in step with them. It is attached in `contracts.invalid_argument`, the one place every tool's schema refusal on this surface is built, so it reaches the caller in the result and not only through `agentic-hil://reference/errors`. `can_adapter_protocol_unsupported` and `can_adapter_invalid_response` gained entries for the same reason, attached at their three raise sites; the second is raised where a frame may or may not have reached the bus, which is exactly when a caller most needs to be told what to do next. Two conversions beside them now refuse by name instead of throwing. `bench_run_start` ran `float()` over `wait_s` before the bench mutex could look at it, which erased a distinction the mutex makes deliberately — it rejects `bool`, and `float(True)` is `1.0`, so a wait nobody could have meant became a one-second wait — and turned a string or a null into a `ValueError`/`TypeError` past the surrounding handler; the raw value now reaches the mutex, and what it refuses is answered as `invalid_argument` naming `wait_s`, with nothing locked and no run opened. The workspace profile's `baudrate` was read with a bare `int()` and has no schema in front of it, so a hand-written `baudrate: fast` ended `agentic-hil init` in a traceback after the board had already been read, and `baudrate: true` would have been converted to `1` and written into the file as a baudrate; both are now a refusal naming `com_ports.<name>.baudrate`, and no configuration is written. (#137)

- **An ordinary user-local installation on POSIX can be registered again, and `doctor` says what was wrong with the candidates it turned down.** `trusted_persistent_executable` walked every ancestor of the launcher and refused any one of them that group or other could write. `~` or `~/.local` at `0775` is the ordinary state on a distribution that combines `umask 002` with per-user groups, and that was enough: `mcp-config` rejected every candidate and then recommended installing persistently with a user-level tool installer, which is exactly what had produced the layout it was refusing. Reported twice from normal, non-editable installations. The walk no longer reads the mode of any ancestor, at any depth, sticky or not — the same detect-rather-than-prevent line Windows has held since its ACL walk was removed in 0.8.0, and for the same reason: the rule could only ever defend against a different account on the same machine, which is not a guarantee this project makes, and it could not defend against the operator's own processes, which own these directories and can re-permission them regardless. What is refused is unchanged and structural. Every component is opened without following a link and held open for the duration; the command must be a regular file or exactly one owner-trusted, single-link launcher symlink whose target contains no further link; neither the file nor the symlink may have changed between the check and the answer; nothing may come from the workspace or a cache/temp root; and the executable itself must belong to root or to this user, carry an execute bit, and not be writable by group or other. One question about a directory survives, and it is about identity rather than permissions: the launcher's own parent must belong to root or to this user, because a directory a third account owns can have the validated file renamed out of it between the check and the registration. Second, and smaller: a refusal was handed on without its reasons. `mcp_server_command` knew each candidate's path, the component that stopped its walk, that component's mode and its owner, and `doctor` passed on the summary alone. `doctor`'s `mcp.rejected_candidates` now carries the per-candidate record, and the refusal that ends the search carries the same structured detail beside each path instead of one sentence. (#143)

- **The pyOCD wording that unlocks the CMSIS-pack remediation is held against the installed pyOCD.** The backend decides that a call failed on an unresolvable `target_type` by matching pyOCD's console prose, and that match is the only thing that reaches the `pyocd pack find` / `pyocd pack install` remediation. An earlier phrase list matched nothing pyOCD prints, so the remediation was unreachable and every such failure fell through to `unknown_debugger_error` with no mention of CMSIS packs — and the only proof that the current phrases fare better was a stand-in reproducing the sentence by hand, which cannot notice a reworded release. The sentence under test is now made by the installed pyOCD, the way the python-can facts behind the CAN classifier are asserted against the installed library, and the two markers the classifier matches on — the `target type` / `not recognized` pair and the `target_support.html` link — are pinned separately so a failure names which one went. The classification is asserted on the phrase path alone: a run applies the `pyocd json --targets` cross-check afterwards, which reclassifies a message the phrases missed and would hide exactly this drift, so the end-to-end half drives a pyOCD whose target enumeration is unavailable and leaves nothing to rescue a match that stopped matching. Where the optional extra is absent — which is the canonical development environment — the module skips and the skip names the extra. One assumption did not survive contact with the tool and is recorded where it was made: pyOCD's command line does not reject an unresolvable target type before it goes looking for a probe, but waits for one, and with `-W` refuses on `No connected debug probes` without ever reaching the type. What makes a boardless test possible is narrower — `Board.__init__` reaches its refusal from session options alone, over the probeless session pyOCD documents as an options container. (#135)

### Added

- `com_ports.<name>.vid` and `com_ports.<name>.pid`, beside `serial_number` and optional like it, and the open-time identity check compares them when they are set (#130). A USB serial number is unique within its vendor and nowhere else, so the check that shipped in 0.9.0 accepted the same serial from a completely different kind of adapter; a matching serial under a foreign vid/pid is now `com_port_identity_mismatch` as well, with `expected_vid`/`expected_pid` and `found_vid`/`found_pid` beside the serials and the hexadecimal pair in the summary. An entry that names the ids and no serial — the cheap CH340 clones publish none — gets a named type check instead of nothing: `identity_source` reads `vid_pid`, and both the confirmation and `doctor` say out loud that it separates one kind of adapter from another and not one adapter from an identical one. `adopt-hardware` and `init` write the ids from the same discovery record that already carried them, reported exactly like the serial. Both spellings load: a number is the decimal pyserial reports (`1155`), a quoted value is the hexadecimal `lsusb` prints (`"0483"`, `"0x0483"`), and both normalise to the integer. A configuration that names neither key is checked exactly as it was.
- **A quarantine that provably involved no hardware can be cleared over MCP, by the agent, with the class boundary intact.** `recover` was CLI-only, so on a host with no shell an agent could see an incident, explain it, and do nothing about it — including one that had never touched a board. The new `hardware_recover` tool clears an incident whose every reason names a call that did not reach the hardware (`lease_release_unconfirmed`, where the action completed and only its record failed to persist; `released_dead_owner_no_contact` from the fix below), gated by the new `permissions.allow_recover` — open in a generated configuration like every grant since the generated defaults were opened in 0.8.0, closable by the agent through `project_config_set` and not reopenable by it, exactly like the other project-scoped grants. What no grant reaches is the class boundary: a reason that needs somebody to look at the board is refused with `recovery_requires_physical_check` carrying the exact `agentic-hil recover --confirm-safe-state --quarantine-id <id>` line and the per-reason `quarantine_guidance`, and there is deliberately **no confirmation argument in the tool's schema at all** — a flag the agent sets for itself is not a confirmation of anything about a physical board, and a test pins the absence. The clearable set is deliberately narrower than what machine recovery may settle: that path is allowed a wider set because it *performs* something — reaps processes, re-reads the probe, under `reset_halt` drives the target into a defined state — and this call performs nothing, so a reason whose settlement is a predicate stays with the predicate and the refusal says so (`auto_recoverable`, `auto_recover_policy`). A recovery through the tool writes the `recovery.jsonl` line with `actor: agent`, `via: mcp:hardware_recover` and `attestation: no_contact_reason_class`, against the CLI's `actor: human` and `attestation: operator_confirmation`, so the ledger says which of the two ways in was taken. Not read-only, not destructive, idempotent — a bench with no open incident answers `ok` with `was_quarantined: false`. (#130) *(The schema gained one optional argument later in this release — see the `operator_statement` entry under Changed. The confirmation boolean described here is still absent and still pinned.)*

### Changed

- **A failed run aborts into a recovery action instead of leaving a padlock on the bench.** When something goes wrong during a run, the run stops and its result is `failed` — that is the verdict, and nothing here softens it. What follows is new: the abort calls a recovery action, so the next run has a board to start on. The seam hangs on the run teardown rather than on one caller, and two callers reach it — the test reactor's abort path, and `bench_run_stop` for an interactive run that ended with an incident standing. It reaps this owner's leftover debugger processes, drives a reset into halt where `recovery.auto_recover` and the probe's `allow_reset` both permit it, and re-reads the probe. The run result gains a `recovery` block naming the actions and the outcome, or naming why nothing was attempted (`auto_recover_policy_off`, `allow_reset_missing`, `probe_not_permitted`), so a bench that quietly never recovers is legible to its operator instead of silent. `ok` stays `false` throughout: recovering the bench does not un-fail a test. What an incident blocks is narrowed to match. The calls that *are* the remedy — `probe_target`, `reset_target`, `flash_firmware` — now run while an incident stands, on the hold the incident left behind, and one that answers the reason the incident names resolves it; the stimulus class waits for it, and `bench_run_start` joins that class, having never been checked against an open incident before. Refusing the reset that settles an incident, on the grounds that the incident was open, was the shape of the old model, and its only way out was a person at a shell. Every resolution — automatic, or performed by a recovery-class call — appends its own `recovery.jsonl` line, evidence first, with `actor: server` and `via: recovery_action` for the performed kind, so no quarantine ends without a record of what ended it. The `audit_broken` families are excluded by construction: they name a ledger that could not be written, and no amount of driving the target writes it, so they keep the operator's route. `recovery.auto_recover` was already `reset_halt` in the generated default and stays there; results now say whether that value was chosen or inherited. Recovery for an *implicit* single-call run — an effect-class tool called with no run open — is follow-up scope and not in this change.
- **`hardware_recover` takes an `operator_statement`, so an agent may relay a claim it still may not make.** The class boundary has not moved: whether a board is powered, still, and holding the firmware somebody expects is a claim about the world, and only a person can make it. What moved is who may carry the sentence. Sending an agent's operator off to find a shell — on a host that may not have one — never protected the board; it only meant the claim was made out of band and the ledger never saw it. Reasons that name a call which never reached the hardware still clear with no arguments. Every other reason is now refused with an instruction instead of a dead end: ask the operator in chat, show them the `quarantine_guidance` while asking, and call again with what they answered, in their words. The statement lands in `recovery.jsonl` verbatim under `attestation: operator_statement_via_agent` — deliberately not the operator's own `operator_confirmation`, because a person quoted by a program and a person at their own command line are different evidence, and an audit that spelled them alike could never tell them apart afterwards. The key is absent, never null, when there is no statement. There is still no confirmation boolean and there will not be, and the difference is the whole design: a flag can be invented by a caller with nothing to go on, while a sentence about a bench has to have been given to it. Nothing here can verify that it was, so the tool description, the refusal and the error catalogue each say outright, first, that inventing one writes a false ledger record with the agent named as the actor who cleared the bench. An empty string is refused by the schema. The `audit_broken` families take no statement either, for the same reason they take no recovery action. `agentic-hil recover --confirm-safe-state` is unchanged and stays in every refusal as the operator's direct route.

### Fixed

- **A dead owner whose session provably never touched the bench was quarantined instead of released.** The 0.8.0 reclassification — a quarantine needs the *possibility* of an effect — had been applied to call failures and never to the owner's death: `coordination.status()` adopted any exited owner whose project record still said `active` as `owner_process_exited_without_release`, without asking what the dead session had done. On the bench that cost an operator a walk and a `recover --confirm-safe-state` after an agent `pkill`ed an already-dead runner whose last call had ended before any hardware contact. `status()` now reads the dead session's own last committed report from the trusted `state_root` before deciding, and releases with the named reason `released_dead_owner_no_contact` — plus a `recovery.jsonl` line carrying `actor: server` — when that report positively proves no contact: it names the record's one open lease and its resources, its tool is one whose lease does not outlive its own call, it carries `side_effect_committed: false` with `side_effect_status: not_started` and an intact audit trail, and its `config_in_force` names the exact configuration bytes the lease record was stamped with. This is the project layer catching up to the bench mutex, which has behaved this way by construction since it existed — the OS drops a dead process's device lock and the next run is handed the device with `reclaimed` and no incident. Everything else quarantines exactly as before, and that direction is the load-bearing half: a committed or partial effect, a report about another lease, a second open lease nothing can answer for, a report from a different configuration, an unreadable report state, or no record at all each leave the incident standing. An unknown is never rounded down to safe. (#130)
- **A SocketCAN session on an interface that does not exist quarantined the bench.** `[Errno 19] No such device` on a `can0` that had vanished after an adapter re-enumeration is the one open failure that is not merely unproven: there is no netdev, so the socket had nothing to bind to and no controller was ever addressed. The classifier missed it because it was written against an expected exception class rather than against what the library throws — it admits only `CanInitializationError` as proof of no contact for SocketCAN, and python-can never raises that class for a failed bind (4.6.1 re-raises the bind's bare `OSError`, and the wrapper it uses elsewhere is `CanOperationError`, which is not a subclass of it). A constructor-time failure whose cause chain carries `ENODEV` is now refused as `can_interface_not_found` with `retry_safe: true`, no incident, the lease released, and remediation naming the channel and the `ip link` lines that bring an interface up. Narrow by construction and by test: constructor time only, `ENODEV` only, SocketCAN only — an `ENETDOWN` or a send failure on a bound socket keeps the markerless result and the quarantine it earns, and the number is read off the `__cause__`/`__context__` chain rather than out of the message. The library facts it depends on are asserted against the installed python-can. (#130)
- **The MCP surface can upgrade its own server, gated by a new `permissions.allow_upgrade`.** `server_upgrade` replaces this installation with the newest release through the package manager that owns it, so a host that is only an MCP client is no longer one on which the main surface cannot perform the basic maintenance of its own server — which is what the CLI-only upgrade of 0.9.0 left it as. The new permission sits with the other project grants: a generated configuration writes it `true` like the rest, and `project_config_set` writes only `false`, so an agent can close it and never open it. Three teeth hold it. *Forward only:* the tool's schema declares no properties and `additionalProperties: false`, so no argument can name a version — an agent that could install an older release could install one that reads `permissions:` under weaker rules, which would make the ratchet reachable through the code. *Honest about the restart:* replacing files does not change what an already-running interpreter executes, so a success reports `upgraded_on_disk` with `previous_version`, `version`, `running_version` and `restart_required: true`, and says outright that this server is the old release until an operator restarts it while the command line is already current — the `config_stale` vocabulary, one layer down. *Refusals rather than half-actions:* `upgrade_in_open_run` while a run or a lease holds the bench (the open-run refusal applied to the code instead of to the permissions, read off `HardwareCoordinator.status()`'s `bench_held`), `upgrade_cli_only_on_host` on Windows, where the files of a running process are locked and `agentic-hil upgrade` at a shell is the way — a detached helper was rejected because it outlives the result that announced it, so its failure would have nobody left to report to — and `upgrade_blocked_by_pin` on a pinned installation, naming an extras-preserving `reinstall_command` it never runs. - **A test plan can drive a CAN bus, and every device kind now answers for itself.** `can_buses` is a first-class section of the authoritative configuration — permissions, `listen_only`, `fd`, `bitrate` — and the MCP surface drives it fully, but the test reactor knew seven actions across two device kinds, so a configured bus could take part in no plan at all and was never even declared or locked by a run, though `CanDevice` has carried its own lock key from the start. ### Development

- **References in the shipped tree point at this repository.** Work is tracked in this repository's issues and pull requests, so a CHANGELOG entry now names the pull request that landed it, and the source comments, docstrings, knowledge texts and test docstrings that carried a reference state the decision they rest on instead of naming one. Nothing described changes behaviour or moves a version, and where the pull request behind an entry could not be identified with confidence the reference is dropped rather than guessed at.
- **A COM port another program was already holding quarantined the bench, and quarantine now presupposes contact instead of inferring it.** Two changes, one cause. *The port.* Serial handles were opened without asking for exclusivity, and on POSIX nothing makes a second open fail: a foreign test runner, an IDE serial monitor or a modem manager could hold the line while a session opened it too, both wrote down one wire, and what surfaced — much later, mid-session — was a reply that did not answer its stimulus. That is an unknown board state, which is a quarantine, and it named the wrong cause: the machine-wide device lock only ever bound the runs that take it. The handle now sets `exclusive` before the open, so a held port fails at the open into the refusal path that has been correct since 0.8.0, with its own error type `com_port_busy` carrying `configured_device`, `retry_safe: true`, no incident, and remediation naming `fuser`/`lsof`, the modem-manager case, and the one thing not to do (sign a physical safe state for a bench nobody disturbed). Classified by OS number off the `__cause__`/`__context__` chain and never off the message — `EWOULDBLOCK`/`EAGAIN`/`EBUSY` only, `EACCES` deliberately excluded because on a serial device it is far more often a missing group membership than a second holder. Windows opens serial devices exclusively whatever is asked for, and its refusal carries no number anywhere, so there it stays `com_port_open_failed`, whose likely causes already name the case; the pyserial facts both halves rest on are asserted against the installed package rather than assumed. *The class of bug.* Three benches in one week were held by failures that never reached any hardware, each one a gap in the same mechanism: a per-backend set of exception classes that prove no contact, with everything outside the set read as an unknown board state. A set of known-innocent classes is only ever as complete as the last incident. Each session and adapter now carries a contact marker, set at the one point per backend where contact is provable — the successful return of the serial `open()`, the successful return of `can.Bus()`, a CAN bridge's own `ok: true` on its open reply — and every failure handler that used to quarantine on a markerless result asks the marker first. A failure before contact is a refusal by construction, whatever exception ended it, including one no classifier has ever seen; a failure after contact quarantines exactly as before. The existing class sets are kept and re-anchored: they can still turn an after-contact failure into a refusal where the class genuinely proves innocence, which is a narrowing the marker cannot make, but they are no longer the only line of defence. Two rules bound it, and both are the point rather than an exception: an unwritable audit trail quarantines regardless of the marker, because a bench whose ledger cannot be written proves nothing about anything; and a state where contact can be neither shown nor ruled out — a bridge handed an open request that never answered, an adapter constructor that failed after it may already have joined the bus — is not innocence, records itself as such, and keeps its containment. Session-scoped reports gain `first_contact_at` (absent, never null, when there was none) with `first_contact_by` naming the proof, and the dead-owner release added earlier in this release consults it as an additional condition: `side_effect_committed: false` is a truthful claim about the *call* that wrote a report, and a session start that opened its port and then failed on its reader thread writes exactly that claim while the open behind it drove DTR and RTS. The marker is what tells those apart. Debugger backends keep their present lifecycle and are follow-up scope.

## [0.9.0] - 2026-08-07

The entries below add surface — two CLI commands, tool annotations, a configuration key, a record in every report, three error types — so this is a minor under decision 0019, not a patch.

Every one of them came from the same place: an interface written from what it was expected to do, never held against what it does. A serial port was identified by a name the kernel hands out in plug order. `listen_only` was read from the configuration, documented as the proof that a reading touched nothing, and dropped before it reached the adapter. `init` looked for hardware only when the project shipped a profile, while every server path looked unconditionally. None of these were found by tests. They were found by using the thing.

That "on POSIX alike" first held only for paths: `probe:` was folded as a host path, which is a no-op on POSIX, so a configured `probe_id: STLINK123` locked `probe:stlink123` (a probe serial is an opaque id, cased everywhere by `fold_hardware_id`) while a hand-written `probe:STLINK123` stayed uppercase — two lock files for one probe. The debugger's executable fallback, the one genuinely path-like component, now takes its own `probe-exe:` prefix, so `probe:` is unambiguously a hardware id folded the hardware-id way on every platform and the two spellings are one lock (#121). Whether two spellings are one *port* remains the host's rule rather than ours, because a serial device name is a path: `com:COM9` folds onto a configured `com:com9` on Windows and stays a second name on POSIX, exactly as the configured entries themselves already behave. (#121)
- Raw resource names stay accepted rather than being refused in favour of `Device` objects, because three callers legitimately have no device to pass: `debugger-discovery:all` names a host-wide enumeration rather than hardware, `project:<digest>` names a configuration, and `adopt-hardware` locks a probe while discovering it — before it is in the configuration and can have a `Device` at all. Those are exactly the names the fold leaves untouched: none of them is a board, and none has a second spelling to collapse.
- **Documenting a result field no longer fails the skill test.** It took every backticked underscored identifier in the shipped skill for a tool name, so each documented field cost an entry in an exclusion list that grew with the documentation and that two branches once extended independently; it now reads the tool names out of the routing table's `The tools` column and holds that column against the tool contract in both directions, and the list is gone. Prose is out of scope by construction, which costs no coverage because the table has to name every tool the server serves — the five `project_config_*` tools, named only in prose until now, gained the row that makes it complete. (#111)
- **A debugger timeout of zero was a configuration the file accepted and every operation then failed under.** `debuggers.<name>.timeout_s` was bounded at `minimum: 0`, so `0` validated and loaded, and it reached the backend as the subprocess wait — where it has already expired by the time the probe is asked. `communicate(timeout=0)` raises within milliseconds, so every probe, flash and reset came back a timeout against hardware that was never given a chance to answer, which reads as a broken bench rather than as a misconfigured number. The bound is `exclusiveMinimum: 0` now, and it is enforced where the number is built rather than only in the shipped schema: the loader refuses zero, a negative and a non-finite value by name at `debuggers.<name>.timeout_s`, so a debugger constructed from a raw mapping is held to the same rule as one read through the validated file. A bound only the schema states is a bound on the file, not on the configuration. Nothing that loaded before stops loading — no shipped template, example or generated default names a zero timeout — and the generated configuration reference renders the new keyword, so the limit is still stated where a reader looks it up. (#127)
- The `max_frame_data_bytes` half of that report no longer held: the loader has branched on `fd` since v0.3.0 — 8 data bytes on classic CAN, 64 with `fd: true` — and the shipped schema, which is the only place the default is written down, already documented exactly that. It is now pinned by a test that reads the default the loader produced and feeds it to the CAN send guard, in both branches, rather than by a sentence nobody rechecks. Separately noted and not changed here: the same key accepts up to 64 on a bus with `fd: false`, where a classic controller cannot carry it.
- **README's tool table and AGENTS.md's configuration table were inventories nothing checked.** Binding the skill's routing table to `evals/install/tools.list.expected` in both directions (#111) left these two to drift the same way: a name no tool answers to and a tool with no row both read as correct. Both are now read the same way — by column, never by prose, because README's notes column alone writes `set`, `describe`, `adopt_hardware` and `reload_description` in the same backticks — and held to the same contract: README's `Tools` column against all 37 tools, AGENTS.md's `Call` column against every `project_config_*` tool the server serves. AGENTS.md's is a partial inventory by design, so it is held to the family it claims rather than to a completeness it never promised; `project_config_create` keeps its place outside it, where README also puts it, because creating a configuration is not changing one, and a tool held out of the table must still be named in the document that holds it out. README's `debug_*` stood for eleven session tools and checked none of them: a wildcard in that column is now refused and the eleven are spelled out, because a prefix that silently swallows whatever arrives next is the one blind spot a completeness check cannot afford. (#123)
- **A lease record was stamped with a second read of the authoritative configuration**, so a file edited in the window between the load and the coordinator that took the lease recorded a document nobody parsed — and `hardware_recover`'s `config_changed` gate, which compares against that stamp, then answered wrong in both directions: it demanded an operator override where the policy in force had not moved, and cleared an incident silently where it had. The stamp now comes from the digest of the bytes that were actually parsed, the same source `reconfigure` already used and the same decision the report stamp makes one layer up, in the unchanged bare-hex spelling that records already on disk carry. (#119)

Each agent also gets a freshly created per-round scratch directory, named in its prompt and not just in its environment, because the agent writes its own `--basetemp` and kept choosing one Windows would not let pytest recreate.

## [0.8.0] - 2026-08-06

The entries below add surface — configuration keys, MCP tools, a resource, a changed generated default — so this is a minor under decision 0019, not a patch.

Three of them change what the tool refuses, and all three came from one working day of using it: the path trust check refused the standard Windows user folders and is gone, a generated configuration granted nothing and now grants everything, and quarantine fired where the failure could prove it never reached the board. What replaced the first is detection rather than prevention; what replaced the other two is a narrower rule that holds. A fourth came from the same day and adds rather than removes: a board written into the configuration is picked up without restarting the server.

All four then went through an adversarial review of the whole range, which found eight defects — three of them in the refusal changes themselves, including two failures wrongly classified as proving they never reached the hardware. Those are fixed here too. A reader deciding whether to upgrade should know that the refusal boundaries moved twice: once by design, once because the first attempt claimed more than it could prove.

### Added

- **A running server says when the configuration it enforces is no longer the one on disk.** It parses the authoritative file at startup and answers out of that version, which is correct and was silent: an operator who switched a debugger from `stlink` to `pyocd` got `pyocd` from `doctor` and `stlink` from `debugger_info` in the same minute, with nothing in either to say which read the file that exists now. Every result now carries `config_status` and `config_stale: true` once the two diverge, `debugger_info`, `project_config_describe` and `doctor` carry the block either way, and the comparison is a SHA-256 of the loaded bytes rather than a modification time — so an identical rewrite is not a change and a change under an unchanged timestamp still is. `changed`, `missing`, `unreadable` and `unknown` are four answers with four remedies — the description reload below, or a restart; restore *then* restart; repair readability *then* restart; nothing, because no file was read to compare against — and `reload_required` from a configuration write now comes off the same check. A file whose bytes are no longer UTF-8 is `unreadable` rather than a restartable change, because no restart can load it. `missing` is reserved for the error that actually says the file is not there, so a path that has become unreachable — an ancestor that is no longer a directory, a permission on the way down — is `unreadable` and gets repair remediation rather than restore-the-file. While the file is `missing`, `project_config_describe` answers out of the loaded policy instead of refusing: `permissions_in_force` is what this server still enforces and `document_source` says whether the values came from disk or from memory. A file that is there and will not parse is refused instead, still carrying `config_status` and `permissions_in_force`, because a caller has to be able to act on it rather than receive an internal error from under the MCP layer; the same normalization covers `project_config_set` and `project_config_adopt_hardware`, which read the document before they change it. `project_config_describe` takes one securely opened byte snapshot and answers both halves out of it, so a response can never pair `state: unchanged` with values read from a newer file. Nothing reloads on its own: the bench's description is re-read only on the explicit request below, and permissions are never re-read at all. (#92)
- An agent can change an existing project configuration over MCP, gated by permissions in the configuration itself (#88). Until now only creation existed: `project_config_create` wrote the file once and the file it wrote refused every further write, so every later correction was hand work on YAML. In the session that produced this decision, that ended with an agent printing a 24-character probe serial for a person to retype.
- **Two permissions, not one**, by the owner's decision. `permissions.allow_config_description_write` opens what the bench *is* — `target.*`, `debuggers.<name>.probe_id` / `executable` / `interface_cfg` / `target_cfg`, `com_ports.<name>.device` / `baudrate`, and every `can_buses.<name>` field except its permissions. `permissions.allow_config_permissions_write` opens the `permissions:` blocks. A single permission for both would have been a master key: set so an agent could enter a probe serial, it would in the same motion have let that agent write `allow_flash: true` on itself, at a point where nobody says so. The invariant from the provisioning ratchet (#77) therefore survives for the common case — the agent reaches the description of the bench, never its own authority.
- `project_config_set` applies named keys with scalar values, each checked against the shipped JSON schema, all of them or none. No argument takes a document and `value` admits no object and no array, so no subtree — and no `permissions:` block hidden inside one — can arrive as a value. The changed document is validated on a temporary file before it replaces the working one, a write is refused while a run or a session holds hardware (`config_write_in_open_run`), and `provenance` records what moved, when, and through which call.
- The split is enforced twice: once by the key model, and once by comparing the permissions actually present in the document before against after. The second check reads the document rather than the request, so it holds where a path parser would not — a permission that moved without `allow_config_permissions_write` fails the write whatever the key was called.
- `project_config_describe` answers, for this configuration in this state, which keys the caller may change, which it may not, which permission would open a locked one, each key's current value and its shape from the schema. Not a general list: after the split the answer differs with what an operator has opened, and a general one would be wrong for most callers. Reading needs no permission.
- New MCP resource `agentic-hil://reference/config-shape`: which sections a configuration has and what each is for, which are required, a worked Nucleo-F446RE example, how to change one over MCP, which permission opens which key, and what deliberately cannot be done. `config-schema` says what is *valid*; this says what a configuration *looks like*, which is what a caller needs in order to write one. Every value shape in it is read out of the shipped schema when it is served, so the two cannot drift — the same principle that makes a refusal and the `errors` resource read one catalogue.
- A `debuggers` / `com_ports` / `can_buses` entry can be added by setting a key under a name that does not exist yet, which is what adopting an attached board needs (#91). The server writes that entry's `permissions` block itself, every flag false, so a device an agent adds can never arrive already allowed to be flashed.
- **A board plugged in after `setup` ran reaches the configuration without hand transcription** (#91). `project_config_adopt_hardware` over MCP and `agentic-hil adopt-hardware` at the CLI read the attached probe and fill in the identity keys that are still unset — probe id, the backend's executable, the detected controller, the probe's own COM device — through `project_config_set`, so the grants, the schema check and the `provenance` record are the ones already there. Both supply no value of their own, cannot name a `permissions:` key, and report a key that already holds somebody's value instead of replacing it; several attached probes, none at all, or a toolchain belonging to another backend are each an answer naming what to do next. Reading the probe is a hardware call and is treated as one by both paths: it takes the same machine-wide locks every board read takes (so a probe another server, run or terminal holds answers `device_busy`), it proves its audit trail writable before touching the board and records the read there, it quarantines fail-closed if the read raises, and on a version 1 configuration it needs the same `allow_probe` that `probe_target` needs. An entry that already names a probe with a different one attached is `hardware_mismatch` and no plan at all, because the identity keys describe one board between them; and the plan is carried into the write as a per-key expectation *and* as the description of the document it was decided against, so a placeholder another writer filled during the seconds the probe took to read refuses the write instead of losing to it — including when what moved is not a key this tool can set, such as the entry's `type` or the `probe_id` that chose which board was read. A concurrent permissions change does not refuse it, because no plan here reads one. An entry carrying its own `target:` block has the detected controller reported rather than written: that block overrides the project target for the probe that was read, so writing the top-level `target.controller` would change the fallback a *different* board uses. And giving the board back is a checked claim — a lease whose release is not confirmed leaves the probe quarantined and refuses the configuration write, instead of reporting a clean read of hardware this process is still holding.
- **A board written into the configuration after the server started no longer needs it restarted** (#104). New MCP tool `project_config_reload_description` and CLI counterpart `agentic-hil config-reload` re-read the bench's *description* — `target`, `debuggers`, `com_ports`, `can_buses`, minus every `permissions:` block — on explicit request, never automatically and never as a side effect of noticing that the file moved. Permissions are not re-read at all, in either direction and under no flag: the grants in force stay the ones parsed at startup, and a device this server has never seen arrives holding nothing, so it can be probed and read and cannot be flashed, reset, mass-erased or written to until an operator restarts. Everything outside those four sections is refused by name in the result — `version`, `workspace_root`, `state_root`, `debug`, `artifacts`, `validation`, `recovery`, `reports`, `logs` and the project grants — because each is either a permission wearing a description key's clothes or a section that mixes the two. Refused while a run, a session or an unresolved incident holds the bench (`config_reload_in_open_run`, `resource_quarantined`) and on a file that is missing, unreadable or does not load. Afterwards `config_status` stops calling the adopted description stale, and carries `permissions_source` whenever the grants in force came from the startup document rather than from the file — so the divergence stays visible without being adopted.

### Changed

- **Quarantine is reserved for an unknown physical state; a failure that can prove it never reached the hardware refuses instead.** Every quarantine trigger was inventoried and classified by whether it can prove its abort point (#102), extending the 0.7.1 `debugger_command_rejected` precedent from one trigger to all of them: a missing toolchain executable (pyOCD, ST-Link CLI, the debug server, GDB), an OpenOCD `-f` script or adapter that failed before the init-stage marker printed — the flash command now carries that marker too, in front of a `program` that runs `init` itself — a pyOCD probe or `target_type` refused before any connect, an absent ST-Link, an unopenable COM port whose handle is verifiably closed, a SocketCAN adapter whose `CanInitializationError` says it never joined the bus, a failed direct CAN read, and a read (`probe_target` / `debugger_probes_list`) whose backend reports that no target answered now refuse with their named `error_type`, `retry_safe: true` and no quarantine record, because each of those left the board exactly as the last call that did reach it did. Everything that cannot prove its abort point — an unconfirmed flash or reset, an exception mid-call, unconfirmed cleanup, a dead owner, a broken audit trail — quarantines exactly as before, and the self-resolving class under `recovery.auto_recover` is unchanged. This supersedes the 0.7.1 entry below that has an adapter which would not open, a target that would not answer and a configuration script OpenOCD could not find still quarantining unchanged: each of those refuses here where its phase evidence is present, and quarantines where it is not. A justified quarantine is now resolvable by a person who was told what they are signing: every quarantined result and `hardware_lease_status` carry `quarantine_guidance` — per reason: what was attempted, what is confirmed, what remains unknown, and the `physical_check` to perform on the board before `recover --confirm-safe-state` — out of one catalogue in `agentic_hil.knowledge`, with an explicit fallback for a reason recorded by another version.
- **A generated configuration grants every permission, and the MCP write path can only take one away.** `agentic-hil init` and `project_config_create` wrote every permission `false`, so a bench was inert until a person found the keys in a YAML file outside the repository and set them by hand — which cost this project's owner a full working day and is why this changed. Both now write every permission `true`, including `allow_raw_debugger_commands`, `allow_mass_erase` and `allow_config_permissions_write`, and the direction replaces the closed start: `project_config_set` writes `false` into a permission and no other value, refused both on the value the request carried and on the permissions present in the document before against after, so an agent can only ever reduce its own authority through it. That claim is deliberately narrow — regeneration is creation and may write open permissions again, and CLI paths are the operator's. Two grants the schema puts on a section rather than in a `permissions` block, `debug.allow_all_symbols` and `artifacts.allow_upload`, are now narrowable too, and `project_config_create` is held to the same open-run refusal and probe lease as every other call that reads a board. (#101)
- **A regeneration reads the board under the whole lifecycle a board read has, and the contracts say what the ratchet actually covers.** `project_config_create` held the enumeration lock and the discovered probe but not the configured entry's own `resource_id` alias, wrote no audit record for the read, and discarded what `HardwareLease.release()` answered — so a board another owner held through that alias could be connected to, and a lease left quarantined still came back as `ok: true` with the configuration rewritten under it. It now runs the same function `project_config_adopt_hardware` runs and is in `audited_hardware_tools()`, so a raised exception comes back as the standard structured quarantine instead of escaping. The generated header, the shipped schema, the `config-shape` resource and `project_config_describe` said the file could only ever narrow; that is true of `project_config_set` and not of regeneration, which grants everything to an entry it meets for the first time, so each of them now names the call the direction belongs to and describes the other door as it behaves — including that the permissions a regeneration carries over are the ones the *writing server loaded at startup*, so a narrowing made over MCP binds that path only after a restart. A server that never bound a configuration but finds one on the in-lock reread — the second of two racing servers — reads the board through that lifecycle too, rather than directly and unleased. And a terminal audit record that cannot be written now raises the incident on the coordinator: the leases are already back by then, so nothing was left to quarantine and the refusal used to carry the pre-failure clean lease status while the next hardware call went through. The security story is the small honest one: the MCP permission-write path can only narrow.
- **An OpenOCD entry that can drive a board is validated like one.** The starter entry was exempt from absolute-script validation and from `doctor` because it still held `interface/stlink.cfg` and `target/stm32f4x.cfg` — and pinning would meanwhile resolve `openocd` off `PATH` for it, so on a host with OpenOCD installed `agentic-hil init` left an entry that granted everything and drove a real program with two unvalidated relative script names. Autodetection no longer runs for the untouched starter entry, which makes it inert rather than exempt, and any entry that names a toolchain is validated whole and checked by `doctor`. Both halves of that are now decided honestly: "untouched" means the skeleton entry with no `probe_id`, `resource_id`, target identity or flash address in it, so a bench somebody identified resolves its toolchain from `PATH` like any other instead of being classified as a starter and skipped; and "can drive" includes the read model, so under version 2 — where reading needs no grant at all — an entry with every mutation permission false is still validated and still checked, because `probe_target` on it starts a real debugger. `agentic-hil init` says so in its next steps instead of promising a bench that works as written.
- **Closing `allow_config_permissions_write` announces itself in the result of the call that does it.** It is terminal for `project_config_set`: after it that call cannot move a permission in the file again. The result carries `permissions_frozen` — what stands frozen and at what value, read out of the written document, that the caller cannot undo it, and `agentic-hil init --force` as the command a person reopens the file with — so an agent cannot nail the bench shut in passing and leave its operator in front of a file they have to edit by hand. Generation and `init` report what they actually wrote rather than a fixed "everything is granted", and `flash_firmware`'s refusal while raw debugger access is granted now names the narrowing that resolves it.
- **A generated configuration permits firmware anywhere in the workspace.** `artifacts.allowed_roots` defaulted to `["build"]`, which no CLion, PlatformIO, or Zephyr tree builds into — `cmake-build-debug`, `.pio/build/<env>`, `out`, `Debug`, `zephyr/build` all miss it, so the list had to be curated before a single flash worked. `agentic-hil init` and `project_config_create` now write `allowed_roots: ["."]`: the whole workspace, recursively. The list was never what stopped an attacker. Containment in `workspace_root` is, and it is untouched — the artifact path still fails on a traversal segment, and a build directory that is a symlink or junction pointing outside is still refused as `within_workspace: false`, which no configuration key relaxes. `allowed_extensions`, `inspect_known_formats` and the SHA-256 of the bytes that reach a backend are unchanged. What the root list added beyond those was a restriction inside the operator's own project, which is still available by naming directories. (#85)
- **Nothing that already exists widens.** The new value reaches an operator through generation only. A configuration that names `["build"]` still means `build`, and one that omits the key is still read as `["build"]` — what an absent key means is exactly what an update may not change (decision 0018). `project_config_create` now carries an existing `allowed_roots` into the file it regenerates, alongside the permissions it already carried; without that, a hardware refresh would have replaced a narrowed list with the skeleton's.
- **A regenerated configuration keeps the artifact extensions its owner set.** `project_config_create` carried `artifacts.allowed_roots` over and left `artifacts.allowed_extensions` to reset, so a bench narrowed to `[".bin"]` came back out of a hardware refresh accepting `.elf` and `.hex` again — three format parsers where a person had permitted one, silently, on a call made to pick up a new probe id. With the roots naming the whole workspace, the extension list is one of the checks that still refuse a foreign artifact, which is exactly why it may not be the one that resets. `artifacts.upload_directory` and `artifacts.max_upload_size_mb` are deliberately not carried: they place a directory and size a payload rather than say what may be flashed, and the same call re-derives `state_root` from the environment on purpose — `debug.allowed_symbols` is carried while `debug.max_dump_size_bytes` beside it is not, and this is that line.
- **`artifacts.allowed_roots: []` is refused at load, by name.** An empty list is one obvious spelling for "no restriction" and equally the obvious spelling for "nothing at all"; here it always meant the second, in line with `debug.allowed_symbols`. The refusal names `["."]` for the whole workspace, naming directories for a narrower set, and `artifacts.upload_directory` for uploads only, rather than let one key mean opposite things to two readers.

### Fixed

- **A description reload validates the configuration it composes, not only the file it read.** Pinning skips an OpenOCD entry's script check when nothing the loaded document permits can drive it, so a version 1 file whose grants are all `false` loads with unvalidated relative script paths — and a reload put this server's startup grants behind exactly those. The composed object is now re-checked and a reload that cannot pass is refused. `permission_summary` also names the version 1 read grants (`allow_probe`, `allow_read`), which it had dropped, so a file that moves only one of them is reported as the divergence it is instead of being called agreement.
- **The abort point of a read is the backend's claim, never the absence of one.** A read-only one-shot is released without quarantine only where the backend positively says it reached nothing (`target_contacted: false`); a markerless failure — killed at its deadline, or a toolchain that exited confirming nothing — quarantines as the new `debugger_readonly_target_state_unconfirmed`, which a read-only re-read may not settle because it attests reachability and the open question is run state. Each backend now names that abort point where it has the evidence: OpenOCD when a target-not-detected classification *read out of its own output* meets an absent init-stage marker, pyOCD and ST-Link on their own connect-failure words, for the two read tools whose command drives nothing. An OpenOCD exit of 0 with the success marker missing answers `probe_unconfirmed` instead, as ST-Link's equivalent exit already did: it is the absence of a report, not a report that nothing answered, and it had been reusing the very classification the evidence rule accepts. Both of those exits now publish `target_state_unconfirmed`, with a catalogue entry of their own, because `target_not_detected` says the adapter was reached and no target answered — the abort-point claim this rule withholds, in the one field a caller reads. A PCAN `CanInitializationError` no longer claims the adapter never joined the bus: python-can raises it from four `SetValue` calls that run after `PCANBasic.Initialize` succeeded, so only SocketCAN can make that claim from the exception class.
- **`target_state_unconfirmed` describes an incomplete confirmation, not an absent one.** Neither backend needs every confirming line missing to reach it — OpenOCD decides on the success marker alone, so the init-stage marker may be in the same output, and ST-Link requires all of its expected lines — yet both catalogue entries said the toolchain reported nothing at all. The result now carries `operation_result` naming which markers arrived and which did not, on both backends, and the entries point at those fields instead of describing a run they cannot see. The quarantine is unchanged: a partial confirmation still names no abort point.
- **`doctor` no longer says a restart is the only way a running server adopts a changed file.** `config_status.compare_with_running_server`, on every `doctor` result, is where a digest mismatch is read, and it still promised restart-only; it now names `project_config_reload_description` for `target`, `debuggers`, `com_ports` and `can_buses`, and the restart for everything else — permissions included, which that call never re-reads.
- **`init` and `setup` no longer chmod an operator's configured paths.** The POSIX smoothing that removed group/other write from every user-owned ancestor of `state_root`, the authoritative config and the agent policy file outlived the configured-path trust check it existed to satisfy; only the MCP launcher chain is still mode-checked, and only it is still smoothed. The shipped guidance also said an unqualified "a permission revoked since startup is already in force" — true of the three configuration-write grants and of no hardware or per-device one, which stay at their startup values until a restart.
- **A reload never renames the document its permissions came from.** `permissions_digest` was moved onto a file whose grants happened to match the ones in force, so a later reload that did find a difference reported that intermediate file as the permission source and paired it with the startup `loaded_at` — two snapshots read as one. It now stays on the startup document for the life of the process, and whether the description in force *states* those grants is its own re-answered field.
- **`state_root` is checked for writability, not only reachability.** An existing directory this process cannot create in loaded clean and failed at the first lease, report or log write; it is now refused at load, with the field named. `config_status` also says which document each half of a stale answer came from (`description_source`, `description_reloaded_at`) instead of claiming everything came from startup after a description reload, and `tools/ci_linux.py` forwards pytest arguments as positional parameters so a `-k` expression or a path with shell metacharacters survives the trip — dropping only its own leading `--`, so pytest's own separator reaches pytest.
- **A COM port is correlated to a probe by the one hardware identity everything else uses.** The correlation stripped punctuation as well as folding case, on the grounds that it keys nothing — but the port it picks is written into `com_ports.<name>.device` by adoption, so a probe serial `AB-CD` matching a sole host port whose serial is really `ABCD` put a different device into an entry whose `allow_write` may already be true. A tie guard cannot see a single false match. A serial the two inventories spell differently is now not correlated at all, and the COM port is reported unavailable with the host inventory attached, for the operator to name.
- **The write comparison sees entries whatever the operator named them.** `permissions`, `provenance` and `allow_anything` are legal debugger, COM and CAN entry ids, and the description projection dropped every mapping key with one of those names at any depth — so an entry called `permissions` was outside the compare-and-swap *and* outside the check for whether a change needs `allow_config_description_write`. A concurrent repoint of that entry from one board to another was invisible, and discovery from the first board could still be committed onto it. The projection now removes the schema's grant locations and only those; a grant found anywhere else survives into it, so it needs the description right as well as the permissions right rather than neither.
- **A failed lease release is now in the audit trail.** Adoption writes the read as an `ok: true`, `lease_state: active` report before releasing, which is right, and then stopped: a release that failed returned `resource_quarantined` while `get_last_report` still described a clean active discovery and `classify_last_error` had no failure at all. The terminal outcome is committed before it is returned, and if that write fails the result is `audit_failed_after_action` rather than silence. The clean path re-commits too, so a persisted record never says `active` about leases that have been released.
- **A partial release is not reported as a released lease.** The aggregate over the enumeration and probe leases took the first non-`active` state it found, so one lease back and one in `cleanup_required` produced `lease_state: released` beside `cleanup_required: true` — and callers are told to treat any state other than null/active/released as blocking. States now aggregate worst-first, the incident's `quarantine_id` travels with them, and each lease's own state is carried so a partial release reads as one.
- **A per-debugger `target:` block is compared before it is reported.** Every override sent the detected controller to `unavailable` with "set this value yourself", including one that already held exactly that controller and one that deliberately held something else — adoption recommending the overwrite it refuses to perform. A matching override is now `already_current`, a conflicting one is `kept` with both values and no recommendation, and only an override with no controller at all is `unavailable`.
- **The opencode write restriction is gone, and `setup` says so instead of implying one.** It never worked. `setup --agent opencode` wrote the two protected trees into `permission.edit` as absolute patterns, and opencode does not compare that key against an absolute path: `write.ts`, `edit.ts` and `apply_patch.ts` all ask with `patterns: [path.relative(instance.worktree, filepath)]`, `evaluate` in `permission/index.ts` matches the configured pattern against that subject, and `Wildcard.match` anchors it `^…$`. Both trees are required to live outside the workspace, so the subject always reads `../../.config/agentic-hil/…` and nothing absolute can equal it. The restriction matched nothing, and unlike the `Write(…)` rule fixed in 0.7.1 it produced no warning to say so. Read out of the opencode source, because its documentation does not say what the patterns are compared against. A correctly relative pattern was written and then dropped again, because it would not have been worth what it claimed: opencode settles this at the prompt, and one "always" answer adds a session rule allowing every later edit that outranks anything the configuration holds — a lock a single click removes should not be presented as one. So `setup` now writes nothing for opencode and reports that it wrote nothing, naming `~/.config/opencode/opencode.json` and `permission.edit` as where the operator sets this if they want it; SECURITY.md carries the reasoning. What a repeat `setup` does do is take back the absolute patterns earlier releases left, by exact text and only where the operator has left them at `deny` — a rule that reads as protection and is none is worse than no rule, which was the whole of this defect. Their own patterns, and any of ours they have since set to another action, stay untouched and in their own order. A test ports opencode's matcher and rule evaluation and shows the removed patterns resolving to `ask` against the subject that host really produces. `claude-code` is unchanged and still gets its `Edit(//…)` rules; Codex still needs none. (#89)

### Fixed

- **An upgrade no longer destroys the installation when the MCP server is running.** Windows refuses to delete a file that is mapped as a running image, and `uv` removes a tool environment before it rebuilds it. Anyone who set Agentic HIL up in an agent host has the MCP server running by definition — the host starts it — so the delete fails, the rebuild never happens, and afterwards there is no installation at all, neither the old one nor the new one. Reproduced on Windows against a throwaway tool environment: `error: failed to remove directory ...\agentic-hil\Scripts: Zugriff verweigert (os error 5)`, with `Lib/` gone afterwards. `agentic-hil upgrade` now establishes whether a process is running out of the installation it is about to replace and refuses with `installation_in_use` before anything is removed, naming each holder by pid and image path so a forgotten one can be found; the installation stays working, and the fix is to close the agent host and run it again. The check has to see past the upgrade itself, which runs out of that same installation: measured on Windows, the interpreter executing the command is imaged at the base Python outside the environment while the process actually holding `Scripts/python.exe` open is its parent, so the current process and the launchers above it are excluded by walking up the parent chain — and a second Agentic HIL, the MCP server this exists to find, is a sibling of the upgrade, never one of its parents. A pid younger than the process claiming it as a parent has been reused and is not followed. The requirement now names every extra whose dependencies are installed. The `uv tool` and `pipx` paths were already correct — both reinstall from a requirement their own receipt records with the extras in it, confirmed against real installations.

## [0.7.0] - 2026-08-03

Reading needs no permission any more; per-device exclusivity took its place. A run names the devices it touches and holds them from its first step to its last, against every process on the machine from one lock directory per user, and a run that dies gives them back instead of leaving the bench blocked. The server now answers for itself over MCP, so a caller with no source tree can look up what a backend field means or what an error wants without reading the implementation, and a failing result carries the fix rather than only the cause. `setup` split into a user half and a project half, so a configuration location the host refuses no longer takes the skill and the MCP registration with it. Where no configuration exists, an agent can generate one over MCP, and the file it writes is what locks it out of writing again.

### Added

- **An agent can generate a project's configuration, and locks itself out doing it.** A project with no configuration answered every tool with `config_file_not_found`, and there was no route past it that did not involve a person at a terminal. `project_config_create` generates one over MCP, filled from `bootstrap` hardware discovery — probe id, controller, the probe's own COM device — and from nothing else: the tool takes no arguments, so it can neither name another workspace nor supply its own content, and a profile lying in the repository does not decide what the board may be told to do. Every write permission in the generated file is `false`, including the new project-scoped `permissions.allow_config_write`, so the reach of the whole path is exactly the reach of reading, which decision 0018 already grants. A person sets `allow_config_write: true` by hand to let the agent regenerate the file later; even then it refreshes hardware facts and carries every permission over unchanged. The file says an agent wrote it, in a header comment and in a `provenance:` block.
- **The ratchet lives in the configuration, and nowhere else.** Two states, both readable from the one file a human inspects: no configuration for the workspace and an agent may generate one; a configuration exists and its own `permissions.allow_config_write` decides whether an agent may write it. There is deliberately no second state store. Deleting a configuration out of band does let an agent generate a fresh one — that is a downgrade, not an escalation, because what it can generate is the fixed deny-by-default skeleton and nothing else, so the round trip costs a human their customised permissions and gains an agent no capability it did not already have. Nothing on the MCP surface deletes or moves a configuration. (#77)
- **`mcp-stdio` starts for a workspace that has no configuration.** It binds the workspace and refuses every hardware tool with `config_file_not_found`, naming the one tool that can do something about it. Only an absent file takes that route: a configuration that exists and does not load is still a hard stop, because reading "broken" as "absent" would let a damaged file be replaced by a generated one, silently discarding the policy an operator wrote. The generation path also picks a `state_root` this profile actually accepts, falling back to `~/.agentic-hil/state` where the documented default under `%LOCALAPPDATA%` is rejected (#78), and returns the same actionable refusal as the CLI where no location passes.
- **Reading needs no permission; exclusivity took its place.** The risk of generous read access in a HIL tool is not damage, it is a false green: a test that disturbs the object under test unnoticed produces a result nobody should trust. That happens when an observation from outside reaches into a running test, and a read permission never prevented it — it only raised the cost of starting, four flags set by hand before the first real Nucleo run did anything. So probing, COM reads and CAN reads need no grant, including the three reads that do perturb the target: attach with halt, CAN receive with ACK, port open with DTR. `allow_flash`, `allow_reset`, `allow_write`, `allow_mass_erase` and `allow_raw_debugger_commands` are untouched and stay deny-by-default. Implements decision 0018.
- **A run holds its devices, machine-wide, for as long as it runs.** The lease each call took was never exclusivity: it ended with the call, so between two steps of a test the board was free. `agentic-hil test-reactor` now locks every device its plan names before the first step and releases them after the last, and refuses a device the plan does not name — the plan is what the mutex can lock, so it has to be the honest record of what a test touches. Contention refuses with `device_busy` and names the holder (pid, host, frontend, run label, since when); waiting happens only when asked for, with `--wait-s`, and is bounded.
- **Devices are a base class, and the agent path got the same run boundary.** Debugger, UART and CAN each derived their own lock name and reached for the mutex in their own shape; the new `agentic_hil.devices` carries the identity, the mutex and one execution shape (`Device.execute(service, action, arguments)`) for all of them. Identity comes from the hardware — `resource_id`, probe serial, serial device, adapter and channel — never from the name of the config entry, so two entries describing one physical unit, such as an ST-Link and its virtual COM port under a shared `resource_id`, collapse to one lock. A declared set is taken in one all-or-nothing acquisition sorted by lock key, so two runs with overlapping devices cannot each hold what the other needs next, and a run whose third device is busy has already given back its first two before the refusal returns. The DUT is deliberately not a device: it is what the devices drive. A debugger entry with neither `resource_id` nor `probe_id` has no hardware to be named after — OpenOCD cannot enumerate probes — so its lock falls back to the toolchain and `bench_run_start` says so in `warnings` instead of presenting it as an identity.
- **`bench_run_start` / `bench_run_stop` / `bench_run_status` close the gap over MCP.** An MCP call took its device *per call*, so an agent driving flash → reset → read held nothing between the steps, and decision 0018's promise held for `agentic-hil test-reactor` only. A run is now declared once with `devices: [{"kind": "debugger"|"uart"|"can", "id": "<config entry>"}]` and holds them until it is closed; inside it only the declared devices may be touched, and a device already held fails the declaration immediately naming its holder. There is deliberately no idle timeout — dropping a device that may be mid-operation is the silent failure exclusivity exists to prevent. A run ends on `bench_run_stop`, on client disconnect (stdin reaches EOF and the server releases it while shutting down), or with the process, where the operating system drops the advisory lock.
- **The lock lives in one place per machine.** `~/.agentic-hil/device-locks`, keyed on the physical device, never under `state_root`: on 2026-08-02 two sessions held the same Nucleo and could not see each other because their `state_root` differed, and a lock kept per configuration is not a bench lock. The home directory is the only location whose ancestors pass this project's own trust check on a stock profile of either platform; the location is fixed and has no environment override, because an override is how two sessions diverge again. Reach is every process of one user on one machine: a directory shared across users is either writable by principals the trust check rejects or needs root to create.
- **A crashed run no longer blocks the bench.** Ownership is the operating system's advisory lock on the lock file, which the kernel drops when the holding process dies. No quarantine, no `recover --confirm-safe-state`, no waiting — the path that held up a run on 2026-08-02. The next owner reports what it reclaimed rather than silently reusing the board.
- **Passive modes are selectable and reported.** `comports.py` did not touch DTR or RTS and therefore took pyserial's defaults, which raise both on open; on a board that wires DTR to reset, listening to a target restarted it. `com_ports.<name>.assert_dtr` and `.assert_rts` now decide it, applied before the port is opened rather than after, both defaulting to the previous behaviour. They are reported in `com_ports_list` beside the device, so a reader can tell a passive observation from one that reset the board. With `can_buses.<name>.listen_only` they are no longer a precondition for access, but they remain the way to observe a target provably undisturbed.
- **The server publishes what it knows about itself over MCP.** `resources/list` and `resources/templates/list` answered with empty arrays and `resources/read` did not exist, so the only way to learn which fields a debugger backend needs, which `target_type` a board takes, or what an `error_type` means was to read the implementation. Measured over two bring-up sessions: 17 such reads, 10 of them inside the *installed* package under `site-packages`, which is what a caller who installed with `uv tool install` and has no source tree is left with. Six resources under `agentic-hil://reference/`: `debugger-backends` (which of `type`, `executable`, `probe_id`, `target_type`, `interface`, `interface_cfg`, `target_cfg` and `flash_address` each backend requires, discovers, or ignores; when `probe_id` becomes mandatory; when `flash_address` is needed), `errors` (every `error_type` with its meaning, ordered fix, and the wrong fix that looks right), `target-support` (which field names the target per backend, known-good Nucleo-F446RE values, and the fact that pyOCD target types come from installed CMSIS packs), `platform-paths`, `lease-lifecycle`, and `config-schema`. Two resource templates serve one entry each: `agentic-hil://reference/errors/{error_type}`, optionally scoped with `:<field-or-backend>`, and `agentic-hil://reference/debugger-backends/{backend}`. `initialize` names them, because it is the only thing said before the caller decides anything.
- **A failing result carries the fix, not only the cause.** New `remediation` (ordered steps) and `do_not` (the wrong fix that looks right) travel beside `likely_causes` wherever a fix is known: every `unsafe_configured_path` refusal, and per backend `target_not_detected`, `adapter_not_found`, and pyOCD's `target_type_invalid`. A rejected configuration path now names a location whose ancestors pass the trust check and rules out relaxing an ACL, which is the obvious response and the wrong one. An `error_type` with no written fix gains neither field. Results and the `errors` resource read one catalogue, so the reference cannot drift away from the refusal.
- **`agentic-hil upgrade`** upgrades the installation running the command, then verifies it. It selects the manager that owns this interpreter — `uv tool`, `pipx`, `uv pip`, or `pip` — rather than whichever `agentic-hil` resolves first on `PATH`, so a second copy is never upgraded by mistake. `--agent <agent>` (repeatable) reinstalls that agent's skill afterwards from the new code, in a temporary directory so no project config is read. The result reports `previous_version`, `version`, `manager`, and `restart_required`; agent hosts must be restarted to load the new MCP server.
- With `agentic-hil.config.example.yaml`, `setup` and `init` locate STM32CubeProgrammer, require one ST-Link, identify it via HOTPLUG, match its COM port by USB serial, and write host values externally. This pre-policy path cannot reset, halt, erase, flash, run raw commands, or access serial I/O.

### Changed

- **`setup` is split along its scope boundary and still works as one command.** One transaction, one rollback set and one smoothing pass spanned two scopes with different lifetimes: skill plus user-level MCP registration (user scope, once per user and agent), then authoritative config plus `doctor` (project scope, once per project). New `agentic-hil agent-install --agent <agent>` is the user half — skill, registration, persistent-trusted-executable check — needing no workspace and no readable configuration; it writes only under the invoking user's home, so per user and per machine, not shared with another OS user on the host. `agentic-hil init` is the project half: it now runs `doctor`, takes an optional `--agent` for the write restriction, and keeps a config it finds instead of refusing, so both halves are idempotent. `setup` runs the two in order, and rollback stays inside its own half in both directions. So on a stock Windows profile, where `%APPDATA%` fails the ancestor trust check, the configuration refusal no longer takes the skill and the MCP entry with it: `setup` reports `ok: false` with `scopes.user.ok` true, leaving a working agent and one location to fix. `--force` still reaches the user half only; rewriting an authoritative config remains `agentic-hil init --force`.
- Profiles may request flash, reset, artifact, and UART access; raw commands and mass erase stay denied. The config a profile produces is version 2, so a probe or read request in a profile written against version 1 is already satisfied and is dropped rather than written into a file that version would refuse. No profile means everything that writes or changes state stays denied; existing operator configs remain untouched.
- Windows discovery includes versioned `C:\ST` CubeCLT, PATH, standalone CubeProgrammer, and CubeIDE installs.
- **Configuration `version`, and an explicit migration.** A file with no `version:` key is read under version 1, where reading still needs `allow_probe` / `allow_read`, so an update never widens what an existing bench allows. `version: 2` selects the new model; a version 2 file that still carries a read permission is refused by name with the key to remove, because ignoring it would leave an operator believing a flag still gates something. `agentic-hil init` writes `version: 2`.
- `agentic-hil doctor` checks the probes whose toolchain the configuration pinned rather than the probes that may be read. "May be probed" is now universal and says nothing about what a bench is meant to drive; using it would have made a freshly written config demand a debugger toolchain before `setup` could finish.

### Fixed

- **A device lock key folded case on Windows and preserved it everywhere else.** Every key was built through `os.path.normcase`, which lowercases on Windows and does nothing at all on POSIX. That is the right rule for the two components that really are host paths — a debugger executable, and a serial device such as `COM7` or `/dev/ttyACM0` — and the wrong one for the components that name hardware: a `resource_id`, a probe serial, a CAN channel. `0669FF` and `0669ff` are one ST-Link on every operating system, so two config entries naming one physical unit in two spellings collapsed to one lock on Windows and stayed two locks on Linux and macOS, with no error on either — the same bench, two different exclusivity guarantees. Opaque hardware identifiers now fold identically everywhere, and path-like values still fold as their own filesystem does. Because folding can also merge, config load now refuses two entries whose `resource_id` values differ only in case: an identical id is still how an ST-Link and its virtual COM port are declared one unit, but two spellings of one id are a question for the operator rather than a merge behind their back. Device locks are ephemeral files under `~/.agentic-hil/device-locks/` that the operating system drops with the holding process, so changed keys need no migration.
- `agentic-hil setup` reported a rejected default state directory under `field: user_config`, labelling a `state_root` failure as one about the configuration file — and, with remediation attached, it would have proposed moving `config.yaml` to fix a state directory.

## [0.6.0] - 2026-08-02

An unattended loop no longer stops at every quarantine. The owning process clears the failure classes it can actually verify, and the audit records what verified them.

### Added

- **The owning process recovers its own quarantines.** A blocked hardware call attempts recovery before refusing: it reaps this owner's leftover debugger processes, verifies the safe state, writes a `recovery: machine_attested` report, and then runs. Previously a quarantine could only be cleared by a person running `agentic-hil recover` — for every class of fault, including ones no person can add information to, such as an OpenOCD process that died mid-cleanup.
- **`recovery.auto_recover` policy** (`off`, `readonly`, `reset_halt`; defaults to `reset_halt`) with `recovery.max_attempts` (default 3) bounding attempts per incident. `readonly` reaps processes and re-reads the probe, which connects without resetting on every backend and therefore cannot alter the state it attests to. `reset_halt` additionally drives a reset-into-halt, which is what settles an unconfirmed flash, reset, or debug-session start. Set `readonly` if anything on the bench reacts to a target reset.
- **`lease-status` reports why, not just that.** New `cleanup_reasons`, `auto_recoverable`, and `auto_recover_policy` fields answer whether to retry or fetch an operator. `cleanup_reasons` also travels on lease-carrying tool results and into the project record, so a second process sees it. The reason previously existed only inside the on-disk marker's `errors[]`, so classifying an incident meant opening state files under the state root.
- **Machine-recovery provenance in reports:** `safe_state_predicate` (`readonly_probe` or `reset_halt`), `auto_recover_policy`, and `auto_recover_policy_source` (`config` or `default`). A config that never names the policy gets the default plus a one-time `warnings` entry the first time recovery resets its target.

### Changed

- One-shot debugger failures no longer share one undifferentiated quarantine reason. Read-only calls (`debugger_probes_list`, `probe_target`) raise `debugger_readonly_result_unconfirmed`, which a re-read settles; `flash_firmware` and `reset_target` keep `debugger_result_unconfirmed`, which needs the `reset_halt` predicate because either may have left the target running.
- A one-shot call that quarantined kept its lease registered but unreachable, so nothing in the process could ever resolve it. The lease is now retained for recovery and released once the safe state is verified.
- Under the default policy a failed `debug_start_session` load is settled by machine recovery instead of waiting for an operator. Recovery halts and never runs the target, so control is not handed back to a partially written image; flashing and running it again stays an explicit, permissioned act. Set `recovery.auto_recover: "readonly"` to keep the previous behaviour.

Excluded from machine recovery regardless of policy: a broken audit (`*_audit_broken`), an incident adopted from an owner that died, a mix of reasons, a still-active sibling lease, an incident whose resources this owner no longer fully holds, and any bench without `allow_probe`. `reset_halt` degrades to `readonly` when the bound probe lacks `allow_reset`. The `machine_attested` report is written before the state transition, so a failed audit write aborts the recovery instead of silently unblocking hardware.

### Fixed

- The CAN receive-queue drain budget bounds time spent talking to the adapter instead of also covering the `queue_clear_start` audit write that precedes it. The one-second deadline was armed before that write, so a slow first append — a cold runner creating the JSONL log while a scanner holds it — could consume the whole budget and break the loop before a single frame was read, failing `can_session_start` with `can_queue_clear_limit` and `frames_drained: 0` on a queue that was never touched.

## [0.5.0] - 2026-08-02

### Changed

- **BREAKING — permissions moved onto the device they authorize.** The top-level `permissions:` block is gone. A debug probe carries `allow_probe`, `allow_flash`, `allow_reset`, `allow_raw_debugger_commands`, and `allow_mass_erase` under `debuggers.<name>.permissions`; a serial port and a CAN bus each carry `allow_read`/`allow_write` under `com_ports.<name>.permissions` and `can_buses.<name>.permissions`. Every flag stays deny-by-default and now has exactly one owner, so enabling flash on a bring-up board cannot grant it on a second board sharing the project config. Loading a config that still declares the old block fails closed with a per-flag migration map instead of a bare unknown-field error.
- **BREAKING — every debug probe is a named `debuggers` entry.** The single top-level `debugger:` block is gone; the name is the routing key a test plan step uses. A project with exactly one probe binds it automatically and needs no name anywhere. The MCP tool surface drives that single bound probe: with several configured, debugger tools refuse with `not_supported` and point at `agentic-hil test-reactor`, which routes per step by name. Two entries that resolve to the same physical probe are rejected at load. A probe_id is required before a board is actually driven rather than at load, so the ids can still be discovered — it is the only field the backends turn into `adapter serial` / `sn=` / `--uid`, so without it two names would drive whichever probe is plugged in.
- **BREAKING — the `devices:` block is gone.** It only bound a debugger to a UART, and both are now addressed by their own names. Test-plan steps carry `debugger: <name>` for flash/debug actions and `port_id: <name>` for UART actions instead of `device: <name>`. A per-board target override moved from `devices.<name>.target` to `debuggers.<name>.target`.
- **BREAKING — the test plan format is version 2.** Version 1 steps addressed a `device:` that no longer exists. A version 1 plan is refused by name, with the key that replaced it for each action, rather than failing on a bare version mismatch.

### Fixed

- A pyOCD `probe_id` is resolved to the one full probe UID it selects before any board is driven. pyOCD matches `--uid` as a case-insensitive *substring* of a probe's unique ID and strips an optional `<type>:` prefix first, so a configured value could select a board the operator never named and two different values could select one board. Zero matches and ambiguous matches are refused before the command runs; config load itself stays hardware-free.
- Config load rejects one `probe_id` that contains another, and treats `stlink:ABC` and `ABC` as the same selector, since that is how pyOCD reads them.
- A project with several probes and no `probe_id` yet now loads, so `agentic-hil debugger-probes` can be used to discover the ids. Requiring the id at load made the documented bootstrap circular: the ids could only be learned from a config that would not load without them. The requirement moved to the point where a board is actually driven, and the refusal names the discovery command and OpenOCD's inability to enumerate.
- A firmware artifact reached through a symlink or junction that leaves the workspace is now refused by name. Containment was computed lexically, so such a path was reported as `within_workspace: true` and fell back to the misleading "must be a single-link regular file" wording — on exactly the case where naming the reason matters most.
- A debug dump into an allowed artifact root that is itself a link inside the workspace is no longer falsely refused. `validate_output_path` resolves symlinks while `artifacts.allowed_roots` are pinned lexically, so the two disagreed whenever a root was a link (pre-existing).
- A per-probe `debuggers.<name>.target` override is applied when that probe is bound, including the automatic binding of a single configured probe. It was parsed and then only honoured for probes other than the bound one, so on the supported single-probe path it was silently dropped.
- A firmware artifact outside `workspace_root` is now refused with that reason instead of "must be a single-link regular file" carrying a `backend_error` about an *output* file, and the `validation` block reports `within_workspace`. A debug dump whose `output_path` leaves the workspace is refused by the same check during reactor preflight rather than after the plan has already flashed and halted the board.
- `write_intel_hex_file` requires a `workspace=` argument and passes it to `atomic_write_text`, so the one write primitive an agent aims at a path of its own choosing carries containment at the write itself, not only in the caller's earlier directory check.
- `stage_for_backend` refuses an artifact whose content was never validated. With `validation.require_existing_file: false`, validation of a file that does not exist yet skips the size, format-plausibility and hash checks entirely; a file appearing before staging was then flashed unchecked.
- Refusals raised while staging an artifact no longer quarantine the probe lease. They happen before the backend is called, so they now carry `side_effect_committed: false` instead of being recorded as an unconfirmed hardware effect that puts a bench into recovery.
- `agentic-hil doctor` resolves and version-checks the debugger toolchain of every probe that grants `allow_probe`, reporting each result under `debuggers.<name>.check`. It previously checked only the bound probe, so a multi-probe project — where nothing is bound — reported `ok: true` with the check silently skipped and no named entry verified at all. The check proves each probe's toolchain resolves and runs; it does not open a probe or contact a target, so it cannot detect an unplugged board or a wrong `probe_id`.
- `agentic-hil debugger-probes` enumerates every probe-enabled debugger instead of refusing whenever no single probe is bound. Probe discovery is how an operator obtains the serial numbers a multi-probe config requires, so it has to work in exactly that config; each backend enumerates all attached probes anyway.
- Two debuggers naming the same `probe_id` are rejected even when their `resource_id` values differ. `resource_id` only renames the coordination lease, so it could previously mask two names pointing at one physical board.
- `classify_last_error` works without a bound probe. It reads the last recorded failure of any tool, so a UART-only or multi-probe project can ask what went wrong instead of being told the tool is unsupported.
- A COM port granted `allow_write` without `allow_read` can now actually be written to. Opening the session was gated on `allow_read` alone, and the session is the only route to the port, so the grant was unusable; the background reader and the buffer drain still require `allow_read`.
- A `run_until_breakpoint` step that omits `timeout_s` no longer fails its own contract. Execution sent an explicit `timeout_s: null` that the `debug_continue` schema rejects, while preflight had validated only the call the plan actually described.
- A flash step refused for `allow_mass_erase` says so, instead of naming the `allow_raw_debugger_commands` flag the operator can see is `false`.
- Backend `likely_causes` and error summaries name `debuggers.<name>.executable`, `.flash_address`, `.target_type` and `.probe_id` instead of the removed singleton `debugger.*` keys, so following the remediation advice no longer produces a config that cannot load.

### Removed

- **BREAKING — test adapters.** The `adapters:` config section, the seven `adapter_*` MCP tools, the adapter bridge service, and the simulated NTC example are removed until the first real adapter exists. CAN process bridges are unaffected.
