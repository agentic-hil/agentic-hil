# hilval hq177 on a NUCLEO-F446RE

Generated by the hil-validations bench gate for one bench run; do not edit.

One libopencm3 image, `dual-dac`, for libopencm3 issue #528: the dual-DAC DMA example in `lib/stm32/common/dac_common_all.c` uses the channel DMA API and does not fit the F2/F4 stream DMA. The image first reads known DAC codes back with ADC1 on the DAC pins (PA4 = DAC_OUT1 = ADC1_IN4, PA5 = DAC_OUT2 = ADC1_IN5; PA5 also drives LD2, which loads channel 2 at high codes; buffered codes stay at or below 3700, inside the output buffer's specified range), then runs DMA1 stream 5 channel 7 moving 32-bit words into DAC_DHR12RD on TIM7 TRGO over 12 buffer cycles with the console silent, recording per plateau the ADC readings, DOR1/DOR2, NDTR, the stream's flags and DAC_SR, then shows DMAUDR1 with the stream disabled. Right after the call to the example function the image reads back the DMA stream, DAC and TIM7 registers the example configured, and again after the last plateau. The documentation patch beside the sources splits the example by DMA family; its F4 block is the code in dual_dac_dma.c, whose SHA-256 the image prints so the evidence names the source it was built from. Functional claim only: no analog precision, no sub-microsecond simultaneity.

Run by [Agentic Hardware-in-the-Loop (Agentic HIL)](https://github.com/agentic-hil/agentic-hil): its test reactor flashes each image, resets the board with the serial port open and records what the image prints; `agentic-hil run-evidence` turns each run into a report a reader without the board can check.

Each image prints lines `HQ177 <kind> key=value ...` on USART2 (the ST-LINK virtual COM port, PA2/PA3, 115200 baud) and ends with `HQ177 done`; each plan in [plans/](plans/) waits up to 60 s for every line it waits for. The tests that sent the images judge the values in the serial log; the images print measurements, not verdicts.
