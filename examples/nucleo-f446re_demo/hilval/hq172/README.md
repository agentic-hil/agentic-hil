# hq172: STM32 UART device-PM suspend while CTS holds the transmitter (NUCLEO-F446RE)

A hardware report on Zephyr PR #121031 (zephyrproject-rtos/zephyr), not a competing fix. The PR
bounds the idle waits in the STM32 UART driver's device-PM suspend with
`CONFIG_UART_STM32_SUSPEND_TIMEOUT_US` (a new Kconfig int, default 100000 us) and returns
-EBUSY instead of spinning without a limit, which blocks whichever thread or work queue runs
the suspend.

## The two images

Both are built from one application source, one devicetree overlay and one prj.conf; the Zephyr
tree is the only difference, so any difference in behaviour is the PR's.

* `head`: the PR head `90ccb4f9d4efc6a2886a8c910f7129856667ae04`.
* `base`: its base `3c61a12bdd8b2975b9180abcb80779ad3724a40d`.

The gate freezes both revisions and compares each image's `BUILD_VERSION` with them (CMake
derives it with `git describe` of the tree built; nothing in the build sets it). Both
are built against the workspace's hal_stm32 module at
`c9550199186236d610092f4005f8c9bae2a6bfcf`; the images do not report it, so the gate checks the
workspace's module checkout, like the two Zephyr trees, with `git rev-parse` and `git status` in
the session that built the images, and checks that the build passes exactly those trees and
nothing else.

## What runs on the board

USART1 with hardware flow control, CTS on PA11. Nothing is wired: CTS is held by the pin's own
internal pull-up, so the USART sees CTS deasserted and holds the transmitter. One
byte is written, so exactly one frame waits in the data register (TXE and TC both clear). The
suspend is then run from the system work queue, with a second work item queued behind it as
progress evidence, while a k_timer interrupt releases CTS 300 ms later by switching the pull to
pull-down, independently of the thread that may be stuck. A rescue interrupt at 1500 ms
bounds the spin when it fires, by clearing the CTS-enable bit; the run then reaches its done line
and the gate rejects every repetition the image marked as rescued. If the rescue does not free the
transmitter either, no done line is printed and the gate fails the image.

Each image runs 5 control repetitions with CTS released before the suspend and 100 repetitions
with CTS held, in one identical sequence, and prints raw cycle counts, return codes and
register values per repetition. Timing is measured in the MCU, on the very cycle counter the
driver's wait polls. Images print measurements, tests judge.

## What the gate asserts

* `head`: every held repetition returns -EBUSY after at least the configured limit (9 600 000
  cycles at 96 MHz) and at most that plus 1 ms, the second work item runs right after the
  suspend returns and before the release, and after the release the held frame, a regular
  transfer and the next suspend all work.
* `base`: every held repetition returns 0, but only one frame plus the clock-off epilogue after
  the release interrupt freed CTS, and the second work item runs only then.
* Both: the in-run control that the pull flip really holds and releases USART1, the control
  repetitions with CTS released (return 0, short), the register and build evidence that the
  overlay took effect, and that the head's longest held suspend and the base's shortest are
  separated by the limit.

## Coverage

The F4 USART has no `USART_ISR_BUSY` and no `USART_ISR_REACK` flag, so only the
transmission-complete (TC) wait of the suspend is exercised; the BUSY and REACK waits are not.
CTS is driven by the pin's own pull resistor, so nothing is claimed about modems or external
flow-control partners, and no measurement is external to the chip.

Run by [Agentic Hardware-in-the-Loop (Agentic HIL)](https://github.com/agentic-hil/agentic-hil): its test reactor flashes each image, resets the board with the serial port open and records what the image prints; `agentic-hil run-evidence` turns each run into a report a reader without the board can check.
