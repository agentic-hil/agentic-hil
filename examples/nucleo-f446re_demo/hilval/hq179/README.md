# hq179: Zephyr PR #119508's Pulse IO STM32 timer-DMA backend, measured in-chip (NUCLEO-F446RE)

A hardware report on zephyrproject-rtos/zephyr#119508, which adds a vendor-neutral Pulse IO API
and an STM32 backend where a timer update event requests one DMA word per tick, written to a GPIO
port's BSRR. PR head `f7165025ba97992bd7367d6873f986b4cdca407f`, base
`3e8f38faf93704249745dbc475052848ce39fdaf`, hal_stm32 `c9afc5e80f977e48f9de14c7f6cce1d193ec7181`.
Upstream targets a WS2812 on an STM32F405 board; the F446 is not covered and no LED is attached
here.

## The two images

One Zephyr application, one overlay and one prj.conf. The driver under test is compiled as
application source from a copy of the PR's driver file, so the images differ only by one patch to
that file:

* `before`: the PR's driver as it is.
* `after`: the same file with six changes: the tick period counted as (PSC+1)(ARR+1); the idle
  level written when a channel is configured, after a timeout and after `stop()`; a trailing idle
  word so the last cell lasts a whole tick; and a devicetree `buffer-size` of 0 that no longer
  means a zero-length buffer.

## What runs on the board

Nothing is wired. The driver drives PC0 (and PC1 for a second instance that has no `buffer-size`)
while DMA2 stream 7 copies the GPIOC input data register into RAM on every TIM8 CC4 event, one
sample per 8 clocks. The measurement yields to the product: the driver's stream is the
lower-numbered one and wins every arbitration tie, and both streams run at the lowest priority
level, which the images read back and print. A TIM3 PWM of known period and duty on PC6, a pin of
the same port, is captured in the very same samples and qualifies every window.

Twelve cases run 20 repetitions each: a qualification window, four resolutions (500 kHz, 2, 6 and
8 MHz) with duty 0, 1, period-1, period and above period, a sequence that exactly fills the buffer
and one cell more, repeated transfers, a controlled timeout and a `stop()` each followed by a
normal transfer, the second instance, a looped request, and an idle-high frame. All of it runs
again after the image's own software reset, and the gate asserts both repetition counts.

## What the gate asserts

* The control: the known PWM is measured within a stated tolerance in every window, and the
  sampling stream reports a complete transfer without an overrun. A failure here reports the
  measurement path, not the driver.
* Per cell: each high and low run equals the requested ticks times the tick the registers imply,
  within 16 clocks for one repetition and within 4 clocks for the mean of 20; no extra or missing
  edge; the first and the last cell complete; the idle level before, between and after frames,
  after a timeout and after `stop()`; and a follow-up transfer that works.
* Before and after: for each predicted deviation, the deviation on the unmodified driver and the
  documented behaviour on the patched one, from identical cases through the same path.

## Coverage

The STM32F446RE at 96 MHz, the four measured resolutions, timing relative to the MCU's own clock.
Nothing is said about LEDs, about absolute frequency, about the API's 10 MHz capability floor or
about any speed not measured. The images measure and print raw numbers; the tests judge.

Run by [Agentic Hardware-in-the-Loop (Agentic HIL)](https://github.com/agentic-hil/agentic-hil): its test reactor flashes each image, resets the board with the serial port open and records what the image prints; `agentic-hil run-evidence` turns each run into a report a reader without the board can check.
